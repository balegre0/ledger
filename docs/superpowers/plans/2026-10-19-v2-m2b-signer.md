# v2-M2b: the Signer — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Certificate custody and signatures in a process of their own. A `signer` module (per-company
certificates serving one or both modes; a `.p12` imported through the api without being parsed there, its key
sealed at rest under a per-certificate data key wrapped by a KMS port; or a credential at an INDOTEL-authorized
certification entity; describe, retire, expiry notices; every signature audited), served only by a new `signer`
app over gRPC (`contracts/proto/ledger/signer/v1/signer.proto`, buf lint and breaking in the gate) to callers
holding per-caller tokens with method allowlists; a `SignerPort` client the other apps hand to channels; and the
DO channel switched from the key it held in process to that port, its verifier and trust staying where they are.

**Architecture:** One manifest key makes a module *isolated* (`[data] isolated_in = "signer"`): its schema's
roles belong to the `ledger_signer` login, only the app of that role runs its consumers, jobs, schedules and
server, and every other app assembles it as a client (its API, the port it provides, its routers) while the
worker's fan-out still moves its outbox and inbox. The generic parts of DGII's signature (the hardened XML
reader, the enveloped XMLDSig profile, the rule of what may sign) move by `git mv` from the DO channel into a
minimal `fiscal-kit` (spec §8.4), the one home both the signer and the channel's verifier import. The signer's
custody adapters (sealing, KMS, the two backends) are the only code that touches a private key, and only the
`signer` app may import them.

**Tech Stack:** Python 3.15, uv workspace, grpcio 1.84 (`grpc.aio`), protobuf 7.36, grpcio-tools and
mypy-protobuf (generation, dev only), buf 1.73 (lint, breaking), cryptography 50 (PKCS#12, RSA, AES-GCM), lxml
6.1, SQLAlchemy 2.1 Core + psycopg 3.3, Alembic 1.20, FastAPI 0.143, PostgreSQL 18.6, pytest + hypothesis +
testcontainers, signxml 5.1 (second verifier, tests only).

**Spec:** `docs/superpowers/specs/2026-10-13-ledger-platform-v2-design.md` §1.5 (legal constraint on signing),
§2 rules 7, 9, 10, §3.2 (signer row), §3.3 (signer app), §3.5 (signer events), §3.7 (all of it), §3.9, §3.10,
§4.2, §4.6 contract 12, §5.2 (`grpc`), §6.2 (`ledger_signer`), §6.3, §8.4 (`ports`, `xml`), §9.5 (keys through
`ImportCertificate`), §9.6, §10 (custody, signer data, transport, size limits, audit), §11, §12 (signing
p95), §13, §16.4. ADRs 0001, 0004, 0009, **0010**, 0011. Evidence: `.superpowers/research/06-dgii-facts.md` §6

## Review Focus

The input classes and failure modes most likely to hurt a client that no single feature test would catch. Each
names the task whose tests pin it.

1. **A process that is not the signer reaching key material.** The api, worker or migrate login reading
   `signer.custody` or `signer.certificates`; an app other than `ledger-app-signer` importing
   `ledger_signer.adapters.custody`; a module's assembly opening custody outside the signer role. Expected:
   `permission denied for schema signer` for `ledger_app` in a valid unit; import-linter's custody contract
   fails the gate; the signer's assembly in roles `api`/`worker`/`receiver`/`migrate` builds no custody object
   (asserted by a fake that records construction). Tasks 1, 3, 10, 12.
2. **The wrong caller, a stolen token, a token of another caller.** No `authorization` metadata, a malformed
   one, an unknown token, the api's token on `SignXml`, the worker's on `ImportCertificate`, a previous token
   after rotation ended, two callers configured with one token. Expected: `UNAUTHENTICATED`
   `signer_caller_unknown` before any handler runs; `PERMISSION_DENIED` `signer_method_not_allowed`; the
   comparison is constant-time over digests; the signer refuses to start with a missing, short or shared token.
   Tasks 2, 12.
3. **Secrets leaking through the side doors.** A wrong `.p12` password, a malformed bundle, a KMS that refuses,
   an entity that fails, a document that cannot be signed: every error message, log line, span attribute,
   audit row, event payload and `repr` checked for the password, the token, the credential, the subject's tax
   id and the document's bytes. Expected: none appears (a test feeds sentinel strings and greps every captured
   output). Tasks 9, 10, 12, 13.
4. **Signing at the edge of validity and time.** A certificate expiring between the document's `signed_at`
   and `signed_at + skew`; one not yet valid; `signed_at` far from the signer's clock; a certificate retired or
   replaced while a signature is in flight; two certificates for one company and mode at once. Expected:
   `signer_window_not_covered` / `signing_certificate_not_valid`, `signer_clock_skew` / `signing_clock_skew`,
   `signing_certificate_missing`; one active certificate per (company,
   mode) enforced by a partial unique index under concurrency (two imports at once: one wins, the other
   replaces it, never two active). Tasks 8, 9, 10.
5. **An import retried, raced or replayed.** The same `Idempotency-Key` twice at once, again after success,
   with another bundle, across modes and companies, after a failure (wrong password). Expected: twins wait and
   the second replays (`replayed = true`, `Idempotent-Replayed: true` at the api); another bundle under a used
   key is 422 `idempotency_key_reused`; a failure stores nothing; keys are scoped per organization, mode,
   principal and route. Tasks 12, 13.
6. **Audit before answer.** A signature whose audit row cannot be written (the audit insert fails), a caller
   that cancels after the signature was made. Expected: no signature is returned unless its audit row
   committed; the row holds the caller, actor, company, mode, certificate, profile, document SHA-256 and
   reference, and never the document. Tasks 9, 12.

## Decisions this plan adds (where the spec is silent; the owner may veto any in review)

1. **Isolation is a manifest key, not a name.** `[data] isolated_in = "signer"` (a `Literal["signer"]`
   today; rule of two for any other) replaces the two places that tested `schema == "signer"`
   (`ledger_devtools.sql`) or nothing at all (`ledger_testing.database` granted every schema to `ledger_app`).
   It drives the roles (`SchemaRoles.signer`), the custody import contract, and the runtime's member kinds.
2. **What each role assembles of an isolated module.** Its own role (`signer`): the module alone with the
   platform's schema for schedule leases; its consumers, jobs, schedules, readiness and a gRPC server (a
   resource it hands over); no channel, no other module, no dispatcher (the worker fans the signer's outbox
   out, spec §3.5), none of the platform's own jobs or schedules. Every other role: the module as a client
   (API, ports, routers; a gRPC channel opened as a resource), and its schema only as a *relay-only* member:
   the worker's dispatcher moves its outbox and inbox rows (`ledger_relay`'s grants), nothing else touches it
   (no readiness check of its schema, no runner, no purge). `ModuleParts` gains no `grpc_services` field: the
   server is a resource of the module's assembly (rule of two for a second gRPC server).
3. **The signature's algorithm lives in `fiscal-kit`, its custody in the signer.** Integration checklist item 2
   moved "the signing half" to `modules/signer`; but the channel's verifier needs the same profile and the same
   rule of what may sign, and modules never import countries. So `fiscal-kit` (spec §8.4's `xml`) gets, by `git
   mv` from the channel: the hardened reader (`adapters/xml/parsing.py` → `ledger_fiscal_kit.xml.hardened`) and
   the enveloped XMLDSig profile with the signing rule and a two-phase signing function
   (`signing/profile.py` + `signing/certificates.py` + the profile half of `signing/signer.py` →
   `ledger_fiscal_kit.xml.dsig`). A key is a value a caller passes in; only the signer process holds one
   (rule 7 is about keys, not code). The seed's shape (`SemillaModel`) is DGII's and stays in the channel. The
   verifier, trust, names and stamp stay in the channel unchanged.
4. **Two-phase signing, so the remote backend never sees the document.** `dsig.prepare(document) -> Prepared`
   (checks, digest, canonical `SignedInfo`), then a backend produces RSASSA-PKCS1-v1_5/SHA-256 over
   `Prepared.to_sign`, then `Prepared.complete(signature_value, certificate) -> bytes`. The local backend signs
   with the unsealed key; the remote one sends the entity only the SHA-256 digest of `SignedInfo` (CSC API v2
   `signatures/signHash` shape). `sign_enveloped(document, key, certificate)` is the one-call composition (the
   DO test signer uses it).
5. **Validity at signing is the signer's.** `SignXml` carries `signed_at` (the moment the document states,
   `FechaHoraFirma`): the signer refuses unless the certificate covers `[signed_at, signed_at + skew]`
   (`signing_certificate_not_valid` at the port) and its own clock is within `skew` of `signed_at`
   (`signing_clock_skew` at the port); skew is
   `LEDGER_SIGNER_SIGNING_SKEW_SECONDS` (default 300, the channel's `MAX_SIGNING_SKEW`). Key usage, CA flag,
   RSA ≥ 2048 and key/certificate match are checked at import (refused there) and again by `dsig` at every
   signature. The channel drops its `certificate_validity()` pre-check and keeps its round-trip skew check.
6. **Subject ↔ company is the channel's rule (v2-M3b).** How a certificate names its holder (`VATDO-<rnc>`,
   `IDCDO-<cédula>`) is Dominican; the signer stores the certificate and returns its subject, and the channel's
   requirements (spec §7.6) refuse a certificate that does not name the company. Until then a company can install
   a certificate of another holder; DGII refuses its documents (`secuenciaUtilizada = false`, number released).
7. **Import shapes.** `POST /v1/certificates` takes the bundle as the raw body (`Content-Type:
   application/x-pkcs12`, at most 2 MiB through the platform's `larger_body()`), its password in the header
   `Ledger-Certificate-Password`, the modes in the query (`?modes=test&modes=live`, default the request's mode);
   the api streams the body to `ImportCertificate` in 64 KiB chunks as it reads it, never buffering or parsing
   it (no multipart: Starlette spools large parts to disk). `POST /v1/certificates/remote` takes JSON
   `{"credential": "...", "modes": [...]}`. The deployment says which backends it offers
   (`LEDGER_SIGNER_BACKENDS`); another is 422 `backend_not_offered`.
8. **Modes and replacement.** A certificate serves one or both modes (`serves_test`, `serves_live`). Installing
   one takes its modes from the active certificate of the company that had them; a certificate left serving no
   mode is retired (`retired_reason = "replaced"`); a partial unique index per mode keeps one active
   certificate per (company, mode). `DELETE /v1/certificates/{id}` retires it for every mode (naturally
   idempotent, no `Idempotency-Key`, like revoking an API client).
9. **Idempotency inside the signer.** The api passes `Idempotency-Key` through; the signer reuses the platform's
   `Idempotency.once` (transport-neutral: a unit, an `Attempt`, a stored response) with route label `grpc
   ImportCertificate`, principal = the forwarded actor, and the fingerprint = SHA-256 over the length-prefixed
   (company, request mode, sorted modes, backend, SHA-256 of the bundle or of the credential). The password is
   not in the fingerprint (nothing derived from it is stored): the same bundle and key with another password
   replays the first answer. The stored response is the `ImportCertificateResponse` bytes, status 201.
10. **Expiry notices are jobs enqueued at install, not a scan.** Installing a certificate enqueues, in the same
    unit, `signer.expiry_notice` jobs keyed `<certificate id>:<days>` at `not_after - days` for each of
    `LEDGER_SIGNER_EXPIRY_NOTICE_DAYS` (default `30,14,7,1,0`; past ones skipped). Each job, scoped to the
    company, publishes `signer.certificate.expiring` (public `certificate.expiring`, `days_left`) if the
    certificate is still active, else does nothing. No cross-tenant scan of an RLS table, no extra table. This
    replaces §3.3's `signer.expiry_watch` schedule; the spec line is amended in Task 15.
11. **The signer's own purges.** The worker cannot purge the signer's idempotency keys or done jobs (no
    `signer_purge`/`signer_rw`), so the signer declares `signer.purge_idempotency_keys` and
    `signer.purge_done_jobs` (jobs and schedules, 1 h and 24 h) and hands the platform's purge handlers over for
    its own schema (`maintenance_jobs` gains `kinds=`; Task 3).
12. **Allowlists, and tokens until mTLS.** `api` may call `ImportCertificate`, `DescribeCertificates` and
    `RetireCertificate`; `worker` and `receiver` may call `SignXml`, `SignSeed` **and `DescribeCertificates`**
    (spec §3.7 gives them the two signing methods only; a channel's requirements, v2-M3b, read the certificate's
    validity through `SignerPort.certificate_validity`, which is a describe; it returns no secret).  Each caller has `LEDGER_SIGNER_TOKEN_<CALLER>` and, during a rotation,
    `LEDGER_SIGNER_TOKEN_<CALLER>_PREVIOUS` (accepted by the server only). A token is ≥ 32 printable ASCII
    characters; the server refuses to start with one missing, short or shared between callers; a client process
    is given only its own (compose and the chart pass each pod its own). Compared as SHA-256 digests with
    `hmac.compare_digest`. See "What protects the signer until mTLS".
13. **A client without an address answers 503.** In `api`, `worker` and `receiver` the signer's section is
    optional (`LEDGER_SIGNER_ADDRESS` and the role's token): without them every certificate route and every
    `SignerPort` call raises `signer_unavailable` and the app logs `signer.not_configured` once at start;
    readiness never depends on the signer (spec §3.7). Every test app that assembles all installed modules
    therefore still builds.
14. **`ModuleContext.environment`.** One field (the app's `LEDGER_ENVIRONMENT`) so a module can refuse a
    local-only adapter outside `local`/`test`: the local-file KMS is refused in `staging` and `production`
    (`kms_local_refused`), and creates its key file only in `local`.
15. **Generated gRPC code is `ledger-devtools sync`'s.** Protos live in `contracts/proto/ledger/<module>/v<N>/`
    (package `ledger.<module>.v<N>`, §4.4); `sync` runs `grpc_tools.protoc` (with mypy-protobuf) into
    `modules/<module>/src/ledger_<module>/adapters/grpc/_generated/`, rewrites the generated absolute imports to
    that package and heads each file `GENERATED by ledger-devtools sync`; `check` fails while it is stale. The
    gate runs `buf lint` and, when `main` holds protos, `buf breaking` against `main`.
16. **Public id prefix `crt`**; permissions `signer.certificates.read` (owner, admin, accountant, issuer,
    viewer) and `signer.certificates.manage` (owner, admin). Certificate routes are moded (they require
    `Ledger-Mode`): the list shows the certificates serving the request's mode.
17. **The generic test PKI moves to `ledger_testing.pki`** (`git mv`, Task 4): authorities, issued
    certificates and PKCS#12 bundles are not Dominican; the DO subject helpers (`person`, `organization`) stay
    in `ledger_country_do_testing.pki` and build on it. Module and kit tests then need no country package.
18. **Data-key cache off, bounded signing pool on** (spec §3.7, v1 M3 decisions 5/7/9/10): every signature
    unwraps its data key through the KMS; RSA work runs in `asyncio.to_thread` under a semaphore of
    `LEDGER_SIGNER_SIGNING_CONCURRENCY` (default 4).

## What protects the signer until mTLS (spec §16.4 defers the mesh)

The gRPC port is plaintext (`ledger_platform.grpc.serve_grpc` already says so). Until a service mesh adds mTLS:

- **Network**: the port is never published on a host; in compose it is on an internal network the api and
  worker share with the signer only; in production (v2-M6, Helm) a NetworkPolicy admits only `api`, `worker`
  and `receiver` pods to it and lets the signer reach only PostgreSQL, the KMS and the certification entity.
- **Per-caller tokens and method allowlists** (Task 2): a call without a known token never reaches a handler;
  a caller reaches only its methods; the caller's name is bound for the audit. A process holds only its own
  token.
- **What a stolen api token gives**: import, describe and retire certificates of any company (the api asserts
  the company; the signer trusts it) — no signature, no key. **A stolen worker or receiver token**: signatures
  for any company's active certificate, each audited with caller and reference. No token exports a key: no
  method returns key material, and the signer's tables are reachable only by `ledger_signer`.
- **Residual risk, accepted until the mesh**: a party on the pod network can read tokens and documents in
  transit. Recorded in Task 15's review file for the owner.

## Port contracts for the owner's choices

The production KMS and the certification entity are the owner's (and counsel's, Q5) decisions. The plan builds
the ports, a local-file KMS for development and a fake entity for tests; the real adapters are later tasks with
no change to anything else.

**`KeyManagement`** (`ledger_signer.application.ports`), what any production KMS adapter must honour:

```python
@final
@dataclass(frozen=True, slots=True, kw_only=True)
class DataKey:
    plaintext: bytes = field(repr=False)   # 32 bytes (AES-256), zeroed by the caller after use where possible
    wrapped: bytes                         # opaque, stored beside the sealed key
    key_id: str                            # the master key (and version) that wrapped it, stored per certificate

class KeyManagement(Protocol):
    async def new_data_key(self, context: Mapping[str, str]) -> DataKey: ...
    async def unwrap(self, wrapped: bytes, *, key_id: str, context: Mapping[str, str]) -> bytes: ...
    async def ready(self) -> None: ...     # cheap, no key operation (readiness); raises KmsUnavailableError
```

- `context` is the encryption context `{"purpose": "signer.custody", "organization": …, "company": …,
  "certificate": …}`; the KMS must bind it cryptographically and refuse an unwrap under another (AWS KMS
  `EncryptionContext`, GCP Cloud KMS `additional_authenticated_data`; a KMS without associated data on wrap,
  e.g. Azure Key Vault `wrapKey`, is acceptable only because the sealed key's AES-GCM carries the same
  associated data).
- Old master-key versions stay able to unwrap (rotation never re-seals; `key_id` says which).
- Only the signer's workload identity may call it; the KMS logs every use; same region as the database.
- Errors: a transient failure is `KmsUnavailableError` (UNAVAILABLE, retried by the caller); a refusal
  (permission, wrong context, disabled key) is `KmsRefusedError` (INTERNAL: a deployment defect, alerted).
- Latency budget: p95 unwrap ≤ 20 ms (spec §12: `SignXml` p95 < 50 ms end to end, the cache being off).

**`CertificationEntity`** (the remote backend's port):

```python
@final
@dataclass(frozen=True, slots=True, kw_only=True)
class EntityCertificate:
    chain: tuple[bytes, ...]   # DER, the signing certificate first

class CertificationEntity(Protocol):
    async def certificate(self, credential: bytes) -> EntityCertificate: ...
    async def sign_digest(self, credential: bytes, digest: bytes) -> bytes: ...   # SHA-256 → RSASSA-PKCS1-v1_5
```

- `credential` is opaque to us (the entity's credential id and whatever authorization its contract gives for
  unattended signing), sealed at rest exactly like a private key.
- Shape of CSC API v2 (`credentials/info`, `signatures/signHash` with `hashAlgo` SHA-256 and `signAlgo`
  `1.2.840.113549.1.1.11`); the entity sees only digests, never documents.
- Errors: `EntityUnavailableError` (UNAVAILABLE), `EntityRefusedError` (CONFLICT: credential revoked or
  expired; the certificate is unusable until replaced).
- Our account's own credentials at the entity (`LEDGER_SIGNER_ENTITY_*`) come with the adapter.

```proto
syntax = "proto3";

package ledger.signer.v1;

import "google/protobuf/timestamp.proto";

// The signer (spec §3.7, ADR 0010): signing certificates in custody, and signatures made with them.
// Every call carries its caller's token (`authorization: Bearer <token>`) and its call id (`ledger-call-id`);
// a caller reaches only its methods: api ImportCertificate, DescribeCertificates, RetireCertificate; worker
// and receiver SignXml, SignSeed, DescribeCertificates. A failed call ends with its error kind's status and the error's stable code
// in the trailing metadata `ledger-error-code`. Ids are internal UUIDs, never public ids.
service SignerService {
  // Installs a certificate: a header, then (local backend) the PKCS#12 bundle in chunks of at most 64 KiB and
  // 2 MiB in all; a remote certificate is the header alone. Idempotent by the header's key. The active
  // certificate of the company that served the new one's modes loses them, and is retired once it serves none.
  rpc ImportCertificate(stream ImportCertificateRequest) returns (ImportCertificateResponse);
  // The company's certificates serving a mode, active first.
  rpc DescribeCertificates(DescribeCertificatesRequest) returns (DescribeCertificatesResponse);
  // Retires a certificate for every mode; retiring a retired one answers it unchanged.
  rpc RetireCertificate(RetireCertificateRequest) returns (RetireCertificateResponse);
  // Signs a document (enveloped signature, the root's last child) with the active certificate of the company
  // and mode, once the signature is audited.
  rpc SignXml(SignXmlRequest) returns (SignXmlResponse);
  // Signs an authority's authentication seed the same way; audited as a seed, with no reference.
  rpc SignSeed(SignSeedRequest) returns (SignSeedResponse);
}

enum Mode {
  MODE_UNSPECIFIED = 0;
  MODE_TEST = 1;
  MODE_LIVE = 2;
}

enum Backend {
  BACKEND_UNSPECIFIED = 0;
  BACKEND_LOCAL = 1;   // the key in custody, sealed under a data key the KMS wraps
  BACKEND_REMOTE = 2;  // the key at an INDOTEL-authorized certification entity; we hold a credential
}

enum CertificateStatus {
  CERTIFICATE_STATUS_UNSPECIFIED = 0;
  CERTIFICATE_STATUS_ACTIVE = 1;
  CERTIFICATE_STATUS_RETIRED = 2;
}

enum SignatureProfile {
  SIGNATURE_PROFILE_UNSPECIFIED = 0;
  SIGNATURE_PROFILE_XMLDSIG_ENVELOPED_RSA_SHA256 = 1;  // C14N 1.0, RSA-SHA256, SHA-256, URI=""
}

// Who acts, for the audit: the request id or system call id, and "human:<subject>", "machine:<subject>" or
// "system:<reason>".
message CallContext {
  string call_id = 1;
  string actor = 2;
}

message Company {
  string organization_id = 1;
  string company_id = 2;
}

message ImportCertificateRequest {
  oneof part {
    ImportHeader header = 1;
    bytes chunk = 2;
  }
}

message ImportHeader {
  CallContext call = 1;
  Company company = 2;
  Mode mode = 3;             // the request's mode: the idempotency key's scope
  repeated Mode modes = 4;   // the modes the certificate serves: one or both, distinct
  string idempotency_key = 5;
  oneof source {
    LocalSource local = 6;
    RemoteSource remote = 7;
  }
}

message LocalSource {
  string password = 1;  // opens the bundle; never stored, logged or echoed
}

message RemoteSource {
  string credential = 1;  // the entity's credential reference; sealed at rest like a key
}

message ImportCertificateResponse {
  Certificate certificate = 1;
  bool replayed = 2;  // the answer of an earlier import under the same key
}

message Certificate {
  string certificate_id = 1;
  Company company = 2;
  repeated Mode modes = 3;
  Backend backend = 4;
  CertificateStatus status = 5;
  bytes fingerprint_sha256 = 6;
  string serial_number = 7;  // hexadecimal
  string subject = 8;        // RFC 4514
  string issuer = 9;         // RFC 4514
  google.protobuf.Timestamp not_before = 10;
  google.protobuf.Timestamp not_after = 11;
  google.protobuf.Timestamp installed_at = 12;
  google.protobuf.Timestamp retired_at = 13;  // unset while active
  string retired_reason = 14;                 // replaced, retired, company_deactivated; empty while active
  int64 version = 15;
}

message DescribeCertificatesRequest {
  CallContext call = 1;
  Company company = 2;
  Mode mode = 3;
  bool include_retired = 4;
}

message DescribeCertificatesResponse {
  repeated Certificate certificates = 1;
}

message RetireCertificateRequest {
  CallContext call = 1;
  Company company = 2;
  string certificate_id = 3;
}

message RetireCertificateResponse {
  Certificate certificate = 1;
}

message SignXmlRequest {
  CallContext call = 1;
  Company company = 2;
  Mode mode = 3;
  SignatureProfile profile = 4;
  bytes document = 5;                          // at most 4 MiB, UTF-8, unsigned
  google.protobuf.Timestamp signed_at = 6;     // the moment the document states

}

message SignXmlResponse {

}
```
