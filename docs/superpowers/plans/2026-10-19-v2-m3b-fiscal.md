# v2-M3b: fiscal module, DR e-CF channel wiring and reception — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the DGII spike and thin invoicing into the fiscal path of spec §8.5: a `fiscal-kit` contract package;
a `fiscal` module (enrollments per company × mode × channel × environment with requirements, routing, the
`IssuePolicy` and `Renderer` implementations, the recovery and mirror consumers, the `CompanyDirectory` port); the
`do-ecf-v1` channel assembled as a real channel (schema `do_ecf`, settings `LEDGER_DO_ECF_*`, numbering ranges and
released numbers, the e-CF state machine on the `do_ecf.advance` job that submits once and never resends, RFCE,
buyer delivery, the printed representation, every e-CF type); the `receiver` app (DGII- and emitter-facing seed,
token, reception with a signed ARECF, commercial approval); invoicing's `IssuePolicy` chain, `apply_fiscal_status`
and fiscal mirror (`fiscal[]` on the wire); an immutable archive (`platform.blobs`: a file store for local and
certification work, S3 object lock for production); a fake DGII in the compose stack and an end-to-end test
(invoice → e-CF accepted by the fake → delivered to a simulated buyer → ARECF verified). The spike CLI is retired.

**Architecture:** Contract first (`fiscal-kit` types, then the generic XML parts moved out of `countries/do` by
`git mv`), then the three platform capabilities every later task needs (the *outside* consumer style, `blobs` and the
`ArchivePort` binding, a complete `ChannelContext`), then the Dominican channel's pure domain for every type in
parallel with the `fiscal` module's enrollments and invoicing's extension points, then the channel's adapters,
persistence and jobs, then the integration (`IssuePolicy` → `Channel.issue` → `apply_fiscal_status`), then reception,
delivery and the printed representation in parallel, then the stack and the end-to-end test. Production-only
hardening (S3 object lock, breaker and contingency clock, range voids, revocation, the live-mode gate) is a separate
group off the certification path. Each task ends with `uv run poe check` green.

**Tech Stack:** Python 3.15 (lazy imports, PEP 695, `TypeIs`, deferred annotations), uv 0.13 workspace, FastAPI 0.143 +
pydantic 2.14, SQLAlchemy 2.1 Core + psycopg 3.3, Alembic 1.20, PostgreSQL 18.6, httpx 0.28, lxml 6.1, cryptography
50, python-multipart (receiver uploads), boto3 (S3 object lock; typed with `types-boto3[s3]`), a PDF library and a QR

  and `receiver` roles, a gRPC client implementing `ledger_fiscal_kit.ports.SignerPort` (per-caller token, method
  allowlist: worker and receiver may `SignXml`/`SignSeed`; api `ImportCertificate`/`DescribeCertificates`).
- **A2.** `SignerPort` is (all `@facade` coroutines, `call: SystemCall`, deadline ≤ 10 s set by the client):
  `sign_xml(call, *, company, mode, profile, document, reference) -> bytes` (the document with DGII's enveloped

## Review Focus

The inputs and failure modes most likely to hurt a client that no single feature test catches; each names the task
whose tests pin it.

1. **A document sent twice, or a number given twice.** A job run whose lease is lost mid-submission; a run cancelled
   by its kind's `timeout` while DGII's call is in flight; two workers on one document; a crash between the call and
   the record; a released e-NCF reallocated while the old submission's track id is still listed. Expected: exactly
   one `POST` to `recepcion`/`recepcionfc` per document ever (the fake counts them); the second run finds
   `submission_started_at` and asks `consultatrackids`; a track id received before `signed_at − RECEIPT_TOLERANCE`
   or recorded on an earlier document is never adopted; no e-NCF belongs to two non-rejected documents (property
   test under concurrency). Tasks 10, 18, 19.
2. **The synchronous path racing the recovery path.** `POST /v1/invoices` numbering and signing while the
   `fiscal.commercial_documents` consumer and `do_ecf.advance` run for the same invoice; the signer slow beyond
   the 1.5 s budget; the request crashing after numbering. Expected: one channel document per (invoice, channel),
   one number, at most one signature recorded (a later one discarded, its archive object an orphan), the `POST`
   answers 201 within the budget with `fiscal[]` `numbered` or signed, the worker finishes the rest, the mirror's
   version never goes backwards. Tasks 18, 20.
3. **Hostile inbound traffic at the receiver.** XML with DTD/entities, a 3 MiB body, a body that is not multipart,
   an e-CF whose `RNCComprador` is another taxpayer, a valid signature by a certificate of another RNC or of no
   trusted authority, a replayed seed, an expired token, a token of company A used on B's path, case-varied paths,
   an RNC no company holds or not enrolled in that environment, the same e-CF twice. Expected: 413 before parsing;
   refusals without echoing input; ARECF Estado 1 with the right reason; 404 for unknown/unenrolled RNC; the
   duplicate answered with the stored ARECF; nothing stored but the raw archive copy before the signature verified.
   Tasks 13, 22.
4. **Buyer endpoints as an attack surface.** Directory URLs pointing to private addresses, redirects, `http`, a
   name resolving to a public then a private address, a buyer relaying DGII's seed (F14), an ARECF signed by the
   wrong certificate, a huge or gzip-bombed answer. Expected: SSRF refusals as the spike's tests prove, kept
   through the port; buyer authentication off by default (no seed signed unless the company switched it on); every
   signed buyer seed audited in `do_ecf.audit_events` with the buyer masked; refused receipts archived and the
   delivery marked failed, never retried for an invalid receipt. Tasks 15, 21.
5. **Tenancy and modes across the new schemas.** Every `fiscal` and `do_ecf` tenant table under RLS (generated
   deny-by-default test), a test-mode enrollment never routing a live invoice, a TesteCF range never numbering a
   live document, a received document recorded under the mode its environment implies, live mode refusing any DGII
   host but DGII's and any enrollment without authority evidence. Tasks 11, 17, 22, 31.

## Decisions this plan adds (spec gaps, each with its reason)

The spec is authoritative; where it is silent or contradicts itself, this plan decides as follows. The owner may veto
any of these in review.

1. **The outside consumer style is built in the platform** (Task 3), not a consumer that relays to a job. §3.5 names
   it as the prerequisite for the consumers of §8.5 that call `InvoicingApi`; a relay job keyed by (invoice,
   channel) would lose a newer status enqueued while the job runs (`enqueue` drops a running key) or leave a parked
   job per invoice for ever. A consumer declares `style = "outside"` in its manifest; its handler runs with no unit
   open; the runner deletes the inbox row in a second unit fenced by its lease token; the facade commands it calls
   are version-monotonic or take the event id as idempotency token (rule 4).
2. **`fiscal-kit` is created here** with the ports' shapes of Assumption A2 (Coordination 2).
3. **`Channel.requirements` is a coroutine taking a `SystemCall`** (§8.3 shows a plain method): requirements read
   the signer (certificate validity) and the channel's ranges.
4. **`ChannelContext` gains `auth` and `http`** (§3.10 lists `http`; `auth` is needed for the public `/v1/do`
   routes); the archive is the port `ArchivePort`, bound by the `App` itself from `platform.blobs` (M1 Decision 11's
   typed `Ports`); **`CompanyDirectory` also is the channels' `PermissionSource`** (a channel cannot read
   `IdentityApi`; `fiscal` answers from it).
5. **A pending enrollment objects; no enrollment is commercial-only.** `IssuePolicy.check` answers 422
   `fiscal_enrollment_pending` (with `currently_due`) when the company has a non-disabled, not-yet-active enrollment
   covering the document's kind; with none at all the invoice issues with `fiscal: []` (§7.6). A POS that believes
   it is enrolled is never silently left without e-NCF.
6. **No usable range is an objection** (`do_ecf_range_missing`, 422 at `check`, nothing stored). A range exhausted
   between `check` and numbering parks the document (`range_missing`), woken when a range is registered
   (`Channel.resume(RANGE_REGISTERED)`).
7. **`outcome_unknown` never leads back to `signed`.** §8.6.4 draws `outcome_unknown ─(track ids)─► submitted |
   signed`; the `signed` edge (a resend) is not built (integration checklist 7). The track-id step polls
   `consultatrackids` on the poll schedule for 24 h; without a fresh, unexcluded track id the job parks
   (`outcome_unknown`) for an operator, who may adopt a track id read in DGII's portal (Task 31). In `certecf`
   (no `consultatrackids`) it parks at once. What to do with a document DGII never received is an owner decision
   (Owner item 3).
8. **A submission is marked before it is made.** The submit step records `submission_started_at` in a committed unit,
   then calls DGII, then records the answer in another unit. A run that finds the mark and no answer (the previous
   run's lease was lost, its `timeout` cancelled the call, the process died) goes to `outcome_unknown` and asks for
   track ids; it never submits.
9. **Released numbers: both safeguards.** A number released by `secuenciaUtilizada = false` is allocatable only from
   `released_at + RECEIPT_TOLERANCE` (2 min) on, **and** the track-id step excludes every track id recorded for that
   e-NCF on an earlier document (`do_ecf.submissions`). Either alone leaves a window (clock skew; a listing that
   arrives late).
10. **One outbound call per job run.** Each `do_ecf.advance` run makes at most one DGII call and returns
    `RunAgain(now)` to chain the next step; the kind's `timeout` is 3 min (DGII calls have a 60 s overall deadline),
    so a timeout only ever cancels one known step.
11. **Archive, then record.** A document becomes `signed` only after `put_once` stored its signed e-CF (and RFCE);
    archive failures are retryable. A signature made by a run that then loses the race is archived but never
    recorded: an orphan under object lock, accepted (bytes are small, never sent).
12. **PostgreSQL keeps keys and SHA-256, the archive keeps the bytes** (§6.8). Submission and delivery read the signed
    bytes back with `ArchivePort.get` and check their SHA-256 before sending.
13. **Archive keys**: `<channel>/<mode>/<organization>/<company>/<kind>/<sha256 hex>.<ext>` with `kind` the channel's
    word (the kit checks only its shape, `[a-z][a-z0-9-]{0,31}`; DO's `ArchiveKind` StrEnum: `ecf`, `rfce`, `anecf`,
    `acecf`, `arecf`, `arecf-refused`, `received`, `representation`); `retain_until` = the day stored + 10 years
    (Código Tributario art. 50 h).
14. **Two archive backends**: `file` (local, tests, certification runs: write-once files, read-only) and `s3` (S3
    object lock, compliance mode, `If-None-Match: *`, SHA-256 checksums). `Settings` refuses `file` when
    `LEDGER_ENVIRONMENT=production`. The S3 store is a go-live item, off the certification path.
15. **Receiver base path `/do-ecf-v1/{environment}/{rnc}`** (§3.8 shows `/do-ecf-v1/{rnc}`): a reception's mode
    follows from the environment DGII calls from (`testecf`/`certecf` → test, `ecf` → live); without it a test
    reception could not be told from a live one. DGII registers the URLs per taxpayer and per environment
    (postulación form, Paso 12, OFV), so each registration names its environment. Owner item 2.
16. **Duplicate receptions**: the same bytes (SHA-256) again → the stored ARECF replayed; the same (issuer RNC,
    e-NCF) with other bytes → ARECF `Estado 1`, `CodigoMotivoNoRecibido 3` (duplicate).
17. **Inbound certificate policy**: received e-CF and ACECF are verified with the `INBOUND` profile and
    `CounterpartyTrust` (roots from `LEDGER_DO_ECF_TRUSTED_ROOTS`, the subject naming the sender's `RNCEmisor`/
    `RNCComprador`). DGII acting as sender during certification (Paso 9, Paso 11) is accepted only through explicit
    certificate fingerprints in `LEDGER_DO_ECF_TEST_SENDER_STANDINS`, honoured in `testecf`/`certecf` only (F15's
    rule: a stand-in identity limited to test environments, the chain still required).
18. **The DGII directory cache lives in process** (24 h positive, 1 h negative, 10 000 entries, per replica), not in
    PostgreSQL: a table keyed by RNC across organizations would break §6.6's shard-key invariant.
19. **Buyer authentication is a per-company switch** (`do_ecf.company_options.buyer_authentication`, default
    `false`, `PUT /v1/do/delivery_options`): off, no buyer seed is signed (F14); a buyer whose reception then
    answers 401 fails delivery with `do_ecf_buyer_requires_authentication` (alerted; the client may switch it on and
    retry).

   imports no kit type): fiscal maps the kit's `Objection` and `Representation` onto them field for field.
2. **`IssuePolicy.after_issue` returns `None`** (Task 12's interface), not the spec's undefined
   `FiscalOutcome`: what it did reaches the answer through the mirror, which the route reads again.
3. **The seam before the unit.** `prepare_create` and `prepare_issue` build, outside any unit, the very
   `Invoice` the unit will store (id minted, priced, seller set, a note's invoice read in a unit of its own and
   checked by `Invoice.new`/`issue`), with the clock's times (the unit's replace them), and run
   `IssuePolicies.check` on its `InvoiceInfo` before returning the `Change`. A draft is not checked when it is
   made, only when it is issued. `Change.issues` tells the route to run `after_issue` after the commit.
   `check` is not time-bounded by invoicing (it runs before anything is stored): fiscal keeps it to local
   reads.
4. **Decision 24.** `price` keeps every key of the regime's namespace; the use cases call `refuse_undeclared`
   when the chain is empty (422 `field_unknown`, as before). Another regime's namespace is refused by `price`.
   **Every undeclared value, chain or not, draft or not, must be plain text** (1 to 500 characters, no
   invisible or control character), or an object of at most `MAX_LINES` (1000) fields, each text or an
   object of at most 20 text fields, every name plain text too (422 `field_undeclared_invalid`, naming no
   client text). The wire's `CountryField` matches (outer object up to 1000 entries), so DO's `withholdings`
   (`{"<line index>": {"itbis": ..., "isr": ...}}`) holds one entry per line of the largest document; the
   regime's own object fields stay at 20 text fields (`replaces_ncf`). **Task 20's `check` must**: validate
   each undeclared key against the channels' `FieldDef`s of the company's enrollments (kind, codes, dates,
   withholdings keys being line indexes of the document) and object `field_unknown` (or the channel's
   `*_field_invalid`); and **object `field_unknown` to any undeclared key when no channel routes the document**
   (no active enrollment covering it), since with a non-empty chain invoicing keeps them.
5. **`after_issue` budget**: `ISSUE_BUDGET` = 1.5 s measured from the commit (monotonic clock) across the
   whole chain; each policy runs in `asyncio.timeout(left)` with `budget=left` (never negative). A timeout is
   logged `invoicing.after_issue_timed_out` (warning), any other exception `invoicing.after_issue_failed`
   (error, the error's type name, its traceback through the platform's redacting processors); both are
   counted in `ledger_invoicing_after_issue_outcomes_total{policy, outcome}`. Only a fresh request that
   issued runs it; the answer is read again only when a policy ran or the request is a replay.
6. **Replay re-read** (Decision 23) applies to all three `POST`s (create, issue, void): the stored status and
   headers (`Location` kept), the document read now, `ETag` its current version. The stored body is still the
   whole view (review M6's "store only the id" was not taken: it would change the chassis).
7. **The mirror** (`invoicing.fiscal_statuses`, revision `0002`, RLS `tenant`, PK tenant + `(invoice_id,
   channel)`, FK to the invoice with the tenant): `apply` takes `FOR SHARE` on the invoice row first (unknown →
   `InvoiceNotFoundError`; **voided → `Applied.DOCUMENT_VOIDED`, nothing written or announced**), then
   `INSERT … ON CONFLICT … DO UPDATE … WHERE version < EXCLUDED.version RETURNING`. Concurrent applies are
   tested on PostgreSQL (four equal first statuses: one `APPLIED`; v3 and v2 at once in either order: v3
   kept; one event per `APPLIED`). **A void is refused (409 `invoice_not_voidable`, pointing to a credit
   note) while any mirrored status is neither `rejected` nor `voided`**; the void reads the mirror after its
   `FOR UPDATE`, so it serializes with `apply` (tested). Details are bounded (5 levels, 16 KiB of JSON). No
   audit row (the channel audits; the document does not change). `accepted_by` and
   `UnmirroredAcceptanceError` are gone.
8. **`InvoiceInfo` does not carry the mirror**: fiscal reads its channels' state itself. Add it only if Task
   20 needs it (a field on the DTO, read in the facade's unit).
9. **Event** `invoicing.invoice.fiscal_updated` v1 payload `{channel, status, version}` (public
   `invoice.fiscal_updated`), subject the invoice, **`aggregate_version` `None`** (the outbox keeps 0): ordered
   consumers sort a subject's events by it, and the channel's version would interleave with the document's.
   **Consume it unordered**, keeping the newest per channel by the payload's `version`.
10. **Representation**: its own router (`adapters/http/invoices.representations`), `channel` query required
    (`^[a-z]{2}-[a-z0-9]+-v[0-9]+$`, ≤ 64), the reader permission, the document read first (404
    `invoice_not_found`), a draft never rendered (404 `representation_unavailable`, no renderer asked).
    `RenderedDocument` is `application/pdf` only, at most 10 MiB, its file name
    `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`; the answer carries `Content-Disposition: inline; filename="…"`,
    `Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`. A renderer's
    `UnavailableError` (Task 20's `ChannelNotReadyError`) answers 503 (documented, tested).
11. **Platform**: `ProblemMembers.problem_members` returns `Mapping[str, JsonValue]`, so `invalid_document`
    lists `errors[]` (≤ 20, `{code, field, message}`) and `omitted_errors` (spec §9.6 updated); the
    idempotency docstring says a route may re-read its resource on a replay.
