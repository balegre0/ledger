# R2: Architecture styles and decomposition (evidence review)

Researcher R2 of 7. Angle: architecture styles and decomposition (modular monolith vs microservices, DDD and
bounded contexts, event-driven, CQRS and event sourcing, hexagonal and clean architecture, cells, Conway's law and
Team Topologies, evolutionary architecture, "choose boring technology"). Read-only review of the repo at `main`

## 1. Sources

### Monolith vs microservices (industry cases)

1. **Deconstructing the Monolith: Designing Software that Maximizes Developer Productivity** (Shopify Engineering, 2019).
   https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity [P]
   Shopify's Rails monolith had no internal boundaries; they considered microservices and chose a modular
   monolith: one codebase, enforced component boundaries.
2. **Under Deconstruction: The State of Shopify's Monolith** (Philip Müller, Shopify Engineering, 16 Sep 2020).
   https://shopify.engineering/shopify-monolith [P]
   2.8M lines of Ruby, 37 components with owning teams. What worked: ownership, Packwerk in PR checks, grouping
   by function. What did not: the dependency graph stayed dense (every component depended on over half of the
   others, with cycles), "interface consistency rules" added friction without improving outcomes, some public
   interfaces "just added indirection", and almost no component had a complete boundary. Services are split out
   only deliberately (storefront rendering, card vaulting) because splitting "increases the overall complexity
   considerably".
3. **A Packwerk Retrospective** (Gannon McGibbon and Chris Salzberg, Rails at Scale, 26 Jan 2024).
   https://railsatscale.com/2024-01-26-a-packwerk-retrospective/ [P]
   Packwerk's privacy checks were removed in v3.0 (they pushed people into API design rather than dependency
   design); todo files grew faster than teams could fix violations; static checks missed runtime coupling, so a
   package with zero violations could still fail when run alone. Conclusion: domain-named boundaries do not match
   how code executes ("Code exerts a powerful drive in the direction of function"); running code in isolation is
   a better measure than static metrics. Still, it "provided value in holding the line against new dependencies".
4. **Goodbye Microservices: From 100s of problem children to 1 superstar** (Alexandra Noonan, Segment, 10 Jul 2018).
   https://twilio.com/en-us/blog/developers/best-practices/goodbye-microservices [P]
   One service and repo per destination grew to 140+ services; three full-time engineers spent most of their time
   keeping it alive; shared-library versions drifted. Back to one service: one engineer deploys in minutes, library
   improvements rose from 32 to 46 a year. Admitted costs: weaker fault isolation, a shared dependency upgrade can
   touch many destinations.
5. **Prime Video audio/video monitoring: moving from Step Functions/Lambda to ECS, ~90 % cost reduction** (InfoQ,
   May 2023, reporting Marcin Kolny's Prime Video Tech post; the original URL now redirects to aboutamazon.com).
   https://www.infoq.com/news/2023/05/prime-ec2-ecs-saves-costs/ [S]
   Costs came from S3 round-trips for intermediate frames and Step Functions state transitions; one process with
   in-memory hand-off fixed it. The engineer framed it as specific to their use case, not a general verdict; no
   baseline figures were given, so the 90 % is not independently checkable.
6. **Introducing Domain-Oriented Microservice Architecture** (Uber Engineering, 2020).
   https://www.uber.com/blog/microservice-architecture/ [P]
   About 2,200 critical microservices grouped into 70 domains with gateways and extension points; one investigation
   crossed about 50 services across 12 teams. Advice for small organizations: "it isn't unreasonable to hold off on
   microservices altogether for some time".
7. **Introducing istiod: simplifying the control plane** (Istio project, 2020).
   https://istio.io/latest/blog/2020/istiod/ [P]
   Istio merged its control-plane microservices into one binary: the components were always released together by
   one team, scaling was dominated by one function, and separated components had near-equal permissions, so the
   split bought little isolation.
8. **Istio as an Example of When Not to Do Microservices** (Christian Posta, Solo.io, 2020).
   https://www.solo.io/blog/istio-as-an-example-of-when-not-to-do-microservices [A, expert practitioner]
   The promised benefits of the split never materialized; teams should be willing to change course.
9. **Building GitHub with Ruby and Rails** (GitHub Blog, 2023).
   https://github.blog/engineering/architecture-optimization/building-github-with-ruby-and-rails/ [P]
   GitHub.com has always been a Rails monolith: nearly two million lines, more than 1,000 engineers, up to 20
   deploys a day, weekly Rails upgrades.
10. **The Majestic Monolith** (David Heinemeier Hansson, Signal v. Noise, 2016).
    https://signalvnoise.com/svn3/the-majestic-monolith/ [P, opinion]
    Microservices suit large organizations; a small team (Basecamp: about 12 programmers) should build one
    integrated monolith and avoid the failure modes of distribution.
11. **Stack Overflow: The Architecture, 2016 Edition** (Nick Craver).
    https://stackoverflow.blog/2016/02/17/stack-overflow-the-architecture-2016-edition/ [P]
    A .NET/SQL Server application on 11 web servers; the author notes it could run on one. Evidence that a tuned
    monolith on a relational database carries a very large site.
12. **Kraken Technologies: how we organise our very large Python monolith** (David Seddon, EuroPython blog, 2023).
    https://blog.europython.eu/kraken-technologies-how-we-organize-our-very-large-pythonmonolith/ [P]
    About 27,600 Python modules and around 400 developers; a layered architecture enforced with import-linter
    (which Seddon wrote): a component may not depend on components above it.
13. **How we ship (2026)** (Kraken Engineering, 9 Mar 2026).
    https://engineering.kraken.tech/news/2026/03/09/how-we-ship-2026.html [P]
    The core is still one Django monolith in one repo: almost 15M lines of Python, over 2,000 ORM models, up 50 %
    in a year, over 100 versions a day across 25+ environments. Market integrations are separate services for
    deployment and compliance reasons. Uses Claude and Cursor; every change gets a human review.

### Authorities on decomposition

14. **MonolithFirst** (Martin Fowler, 2015). https://martinfowler.com/bliki/MonolithFirst.html [P]
    Successful microservice systems almost always started as monoliths; microservices-first systems often ended up
    in trouble. Reasons: speed of feedback while you don't know whether the product is useful (YAGNI), and stable
    boundaries are hard to find up front. Options: a carefully modular monolith (API and data modular), peeling
    services off the edge, or a sacrificial architecture you expect to discard.
15. **Microservice Prerequisites** (Martin Fowler, 2014). https://martinfowler.com/bliki/MicroservicePrerequisites.html [P]
    Before microservices: rapid provisioning, basic monitoring, rapid deployment, DevOps culture.
16. **Don't start with a monolith** (Stefan Tilkov, martinfowler.com, 2015). https://martinfowler.com/articles/dont-start-monolith.html [P, counterpoint]
    Splitting a monolith later is extremely hard; if you know the domain very well and the system is large, start
    with separate systems. He concedes that a team able to build a well-structured monolith may not need
    microservices at all.
17. **Sam Newman at QCon London 2020: microservices should not be the default; the modular monolith is underrated**
    (InfoQ). https://www.infoq.com/news/2020/05/monolith-decomposition-newman/ [S]; also The Register,
    https://www.theregister.com/2020/03/04/microservices_last_resort/ [S]
    Newman: "microservices should not be the default choice"; he told half his clients microservices were not for
    them; prefer a modular monolith, with separated data if you want to keep the split option, because the data
    tier is the hardest part to split later.
18. **Modular Monolith: Is This the Trend in Software Architecture?** (Ruoyu Su and Xiaozhou Li, arXiv 2401.11867, 2024).
    https://arxiv.org/abs/2401.11867 [P, grey-literature review]
    A systematic grey-literature review: practitioners present the modular monolith as an alternative to
    microservices and as an intermediate step; three frameworks and four cases identified. A thin academic base:
    the evidence is still mostly practitioner reports.
19. **Kamil Grzybek on modular monoliths and architectural drivers** (InfoQ, Jan 2020).
    https://www.infoq.com/news/2020/01/monolith-architectural-drivers/ [S]
    Choose by drivers (functional requirements, quality attributes, constraints, team, time, budget), not fashion; a
    monolith is defined only by having one deployment unit.
20. **Spring Modulith** (Spring project, official). https://spring.io/projects/spring-modulith [P];
    https://spring.io/blog/2022/10/21/introducing-spring-modulith [P]
    Mainstream frameworks now ship modular-monolith support out of the box: module detection, a verification test
    that fails the build on boundary violations, generated module docs, and an event publication registry
    (a framework-level transactional outbox). Evidence that this repo's hand-built boundary checks and outbox are a
    commodity pattern elsewhere.

### Domain-driven design and enterprise application platforms

21. **Domain-Driven Design Reference** (Eric Evans, Domain Language, 2015, CC BY 4.0).
    https://domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf [P]
    Strategic patterns: bounded context, context map, shared kernel ("keep this kernel small"),
    customer/supplier, conformist, anticorruption layer, open-host service, published language. Core domain
    distillation. (I saw the table of contents and quoted shared-kernel text; pattern bodies via secondary pages.)
22. **Effective Aggregate Design** (Vaughn Vernon, 2011, basis of chapter 10 of *Implementing DDD*).
    https://www.dddcommunity.org/library/vernon_2012/ [P]
    Keep aggregates small, reference other aggregates by id, change one aggregate per transaction, use domain
    events for eventual consistency between aggregates.
23. **Doing more with less, part 2: buy don't build using DDD** (Chris Richardson, microservices.io, Apr 2024).
    https://microservices.io/post/architecture/2024/04/16/doing-more-with-less-part-2-build-vs-buy-using-DDD.html [P, consultant]
    and **Your IDP needs DDD** (Octopus Deploy). https://octopus.com/blog/your-idp-needs-ddd [A]
    Core/supporting/generic subdomains (Khononov's framing): build the core, buy or adopt generic subdomains, keep
    supporting ones simple. (Khononov's book itself not accessed.)
24. **The Salesforce Platform Multitenant Architecture** (Salesforce Architects).
    https://architect.salesforce.com/fundamentals/platform-multitenant-architecture [P, V]; original paper:
    Weissman and Bobrowski, *The Design of the Force.com Multitenant Internet Application Development Platform*
    (SIGMOD 2009), https://pubs.dbs.uni-leipzig.de/cloud/sites/cloud.pubs.dbs.uni-leipzig.de/files/p889-weissman-1.pdf [P]
    The world's largest CRM is a metadata-driven multitenant kernel: tenant objects, fields and logic are metadata
    interpreted at runtime, not tables or code generated per customer.
25. **Frappe Framework: DocTypes** (official docs). https://docs.frappe.io/framework/user/en/basics/doctypes [P]
    ERPNext's base: one DocType definition yields schema, table, controller, REST API, forms, list views,
    permissions and reports; metadata is a first-class citizen.
26. **Odoo developer tutorial: Inheritance** (Odoo 17-19 docs).
    https://www.odoo.com/documentation/17.0/developer/tutorials/server_framework_101/12_inheritance.html [P]
    Odoo modules extend other modules' models in place (`_inherit`: add fields, override methods, call `super()`),
    and views by XPath inheritance: one shared database, extension by inheritance rather than by bounded-context
    isolation.

### Event-driven, CQRS, event sourcing, ledgers

27. **What do you mean by "Event-Driven"?** (Martin Fowler, 2017). https://martinfowler.com/articles/201701-event-driven.html [P]
    Four different things share the name: event notification, event-carried state transfer, event sourcing, CQRS.
    Event notification decouples cheaply but makes the overall flow hard to see because it is in no program text.
28. **CQRS** (Martin Fowler, 2011). https://martinfowler.com/bliki/CQRS.html [P]
    "For most systems CQRS adds risky complexity"; many systems fit a CRUD model and should stay so; apply CQRS to
    specific bounded contexts only.
29. **Greg Young: the biggest event-sourcing anti-pattern is an event-sourced monolith** (InfoQ, Apr 2016).
    https://www.infoq.com/news/2016/04/event-sourcing-anti-pattern/ [S, reporting the originator]
    Building a whole system on event sourcing was the worst thing he saw in a decade; CQRS/ES are not top-level
    architectures and belong in a few places; plain read/write separation on one database is still valuable.
30. **Mistakes made adopting event sourcing (and how we recovered)** (Nat Pryce, InfoQ, Jul 2019).
    https://www.infoq.com/news/2019/07/mistakes-recovery-event-sourcing/ [S, practitioner]
    A team kept a current-state table beside the event history (state no longer rebuildable from events, costly
    migrations) and confused event-driven design with event sourcing.
31. **When not to use Event Sourcing?** (Oskar Dudycz, event-driven.io, 2021).
    https://event-driven.io/en/when_not_to_use_event_sourcing/ [P, practitioner]
    Not a system-wide concept; decide per module; supporting modules such as CMS-like data are better as plain CRUD.
32. **Immutability Changes Everything** (Pat Helland, CACM, Jan 2016; "Accountants Don't Use Erasers").
    https://cacm.acm.org/practice/immutability-changes-everything/ [P]
    Ledgers are append-only: corrections are new entries; the log is the truth and the database a cache of it.
    This is the case for an immutable journal, which does not require an event-sourcing framework.
33. **Ledger: Stripe's system for tracking and validating money movement** (Stripe, 16 Feb 2024).
    https://stripe.dev/blog/ledger-stripe-system-for-tracking-and-validating-money-movement [P, V]
    An immutable, auditable log of money movement at about five billion events a day with automated data-quality
    checks. (Double-entry details seen only in secondary summaries.)

### Hexagonal / clean architecture costs

34. **When to Use Clean Architecture (And When Not To)** (Milan Jovanović).
    https://milanjovanovic.tech/blog/when-to-use-clean-architecture [A]; **Hexagonal architecture in Python**
    (dev.to). https://dev.to/szymon6927/hexagonal-architecture-in-python-1b0b [A]
    Practitioners' advice: start with feature folders and add layers when logic appears; apply ports and adapters
    only to modules with real business logic, not to CRUD modules. No controlled study of the overhead found.

### Cells, organization, evolution, boring technology

35. **Reducing the Scope of Impact with Cell-Based Architecture** (AWS Well-Architected whitepaper, 2023).
    https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/reducing-scope-of-impact-with-cell-based-architecture.html [P, V]
    Cells are complete independent copies of a workload with a fixed maximum size, selected by a partition key
    (for example customer id) through a thin routing layer; no cross-cell calls or shared databases; benefits are
    blast radius, testable maximum size, phased deployments.
36. **Slack's Migration to a Cellular Architecture** (Slack Engineering, 2023).
    https://slack.engineering/slacks-migration-to-a-cellular-architecture/ [P]
    Triggered by a 2021 AZ network fault; AZ-siloed services and edge draining within 5 minutes; about 1.5 years
    for the most critical services, with per-language and per-discovery-system work and services that could not be
    siloed.
37. **Staying in the zone: how DoorDash used a service mesh to manage data transfer** (DoorDash Engineering, 2024).
    https://careersatdoordash.com/blog/staying-in-the-zone-how-doordash-used-a-service-mesh-to-manage-data-transfer-reducing-hops-and-cloud-spend/ [P]
    and InfoQ summary https://www.infoq.com/news/2024/01/doordash-service-mesh [S]
    Cells with blocked intercellular traffic and zone-aware routing, motivated by cross-AZ cost at very large
    microservice scale (excerpts only).
38. **Conway's Law** (Martin Fowler, bliki). https://martinfowler.com/bliki/ConwaysLaw.html [P]
    Architecture mirrors the communication structure of the organization; the inverse Conway maneuver shapes teams
    to get the architecture; recommends *Team Topologies* (Skelton and Pais) for organization design.
    Team Topologies' cognitive-load framing via https://teamtopologies.com/ (book not accessed; summaries only).
39. **Building Evolutionary Architectures, 2nd ed.** (Ford, Parsons, Kua, Sadalage; Thoughtworks/O'Reilly 2022).
    https://www.thoughtworks.com/insights/books/building-evolutionaryarchitectures-second-edition [P]
    Incremental change, appropriate coupling, and fitness functions: automated checks of architectural
    characteristics run in the pipeline.
40. **Thoughtworks Technology Radar** (current volume). https://www.thoughtworks.com/radar [P]
    Deterministic "feedback sensors" (compilers, linters, type checkers, tests, mutation testing) inside coding-agent
    loops; teams reduce architectural drift by combining deterministic structural rules with LLM review. (Volume
    and exact blip wording not confirmed.)
41. **Choose Boring Technology** (Dan McKinley, 2015). https://mcfunley.com/choose-boring-technology [P]
    About three "innovation tokens" per company; spend them on the core mission; every new technology carries
    operational and cognitive baggage whose long-term cost usually exceeds the convenience; boring tools have known
    failure modes. Counterpoint: **Against Innovation Tokens** (Glyph, 2024),
    https://blog.glyph.im/2024/07/against-innovation-tokens.html [A]: the meme lost McKinley's nuance about
    operational overhead.

## 2. What the evidence says about each style, for a solo founder + AI agents building CRM + ERP breadth

**Microservices.** The evidence against them for this situation is close to unanimous. Every advocate puts
organizational scale first: Uber at 2,200 services still advises small organizations to wait [6]; Fowler's
prerequisites (provisioning, monitoring, rapid deploy, DevOps culture) are operations capacity a solo founder does
not have [15]; Newman says not the default [17]; even Tilkov's pro-services argument assumes a large system and a
team that knows the domain well, and concedes that a team able to keep a monolith well-structured may not need
services [16]. Reversals (Segment [4], Istio [7, 8], Prime Video [5]) all cite ops cost growing per service and
components that are always released together. Conway's law [38] cuts the same way: one human plus agents is one
communication structure, so independent team deployability, the main payoff, buys nothing.

**Modular monolith.** Strongly supported: Shopify [1-3], GitHub [9], Kraken [12, 13] (Python, import-linter,
15M lines, the closest analogue to this repo), Basecamp [10], Stack Overflow [11], plus a grey-literature review
[18] and framework support (Spring Modulith [20]). But the best-documented case, Shopify, adds lessons that matter
here: (a) boundaries drawn by domain name do not match runtime coupling; (b) mandatory interface patterns and
privacy rules produced friction and indirection and were partly removed [2, 3]; (c) years in, the graph was still
dense and boundaries incomplete. Strict boundaries are worth having as a ratchet against *new* coupling, not as an
idealized acyclic graph of perfectly encapsulated contexts.

**DDD / bounded contexts.** The strategic half is the most useful tool for this decision: classify core /
supporting / generic subdomains and build only the core [21, 23]. For a DR CRM+ERP, the core (differentiating,
regulated) is fiscal compliance (e-CF, numbering, DGII lifecycle, custody, country packs) and arguably
DR-specific accounting reports; CRM pipeline, contacts, quotes, generic inventory and generic GL screens are
supporting or generic, which DDD says to buy, adopt, or build as simply as possible. The tactical half (small
aggregates, one aggregate per transaction, eventual consistency between aggregates [22]) is sound inside a
context, but applying a context-per-schema, event-coupled model across *all* ERP areas fights how ERP data is used
(see failure modes).

**Enterprise-application style (metadata-driven platform).** This is the style the evidence associates with
*breadth*: Salesforce (a metadata-driven multitenant kernel [24]), ERPNext/Frappe (DocType generates schema, API,
forms, lists, permissions, reports [25]), Odoo (modules extend each other's models and views in one shared
database [26]). None of these succeed through bounded-context isolation; they succeed by making a new entity, field,
form, report or extension cheap. For a solo founder whose agents must produce dozens of entities, the cost per
entity, not the purity of boundaries, decides whether breadth is reachable.

**Event-driven.** "Event-driven" is four patterns [27]. A transactional outbox for integration and side effects
(webhooks, DGII submission, notifications, GL posting) is boring and right. Using event notification as the main
glue *between* modules of one process makes flows invisible in code [27] and forces process managers, which Young
calls hard to build [29].

**CQRS / event sourcing.** Not as a system architecture [28, 29, 31]; teams that adopted it report costly mistakes
[30]. For accounting, the right takeaway from Helland [32] and Stripe [33] is an *append-only ledger table* with
reversals, not an event-sourcing framework. Light CQRS (read models, reporting replica) is valuable; full CQRS/ES
is not.

**Hexagonal / clean.** Worth it where logic is deep and external dependencies volatile (DGII client, signer,
country channels); overhead in CRUD-heavy areas, which is most of a CRM [34]. Apply selectively per module.

**Cells.** A scaling and blast-radius pattern for after product-market fit: whole copies of the monolith
partitioned by tenant [35]. Slack needed 1.5 years with a large team [36]; DoorDash's motivation was cross-AZ
cost at huge microservice scale [37]. For now, the only thing worth paying for is the invariant that makes cells
possible later: a tenant shard key and no cross-tenant uniqueness.

**Evolutionary architecture / fitness functions.** Strongly applicable to AI-agent development: deterministic
checks are the agents' feedback sensors [39, 40]. This is the one place where heavy investment pays more for an
agent-built codebase than for a human team.

**Boring technology.** Postgres for everything (queue, outbox, RLS) is a textbook boring choice [41]. Hand-building
a 17k-line chassis (job queue, outbox/inbox/fan-out, rate limiter, idempotency, manifest code generation, dated API
versioning, gRPC extraction seams) and running on Python 3.15 two weeks after GA spends innovation tokens on
undifferentiated infrastructure; McKinley's point is that the maintenance and cognitive cost, not the build cost,
dominates, and AI agents reduce the build cost, not the cost of one human understanding and operating it.

## 3. Failure modes the evidence documents (and which ones threaten this project)

| Failure mode | Evidence | Threat here |
|---|---|---|
| Distributed monolith: services always released together, ops cost per service | Segment [4], Istio [7], Newman [17] | Low: avoided by ADR 0001 |
| Premature extraction for imagined scale; cost from network/storage hand-offs | Prime Video [5], Fowler [14] | Low today; the gRPC-ready seam per module is a latent invitation |
| Boundary rules that add indirection without value; ceremony agents must reproduce for every feature | Shopify [2], Packwerk [3] | **High**: facades + Protocols + DTOs + events + manifests + generated contracts per module; ADR 0011 already had to invent "flows" because the acyclic rule (imports *and* subscriptions) blocked mutual reactions at four modules |
| Domain-named boundaries that do not match runtime/data use | Packwerk [3] | **High for ERP**: reporting, document chains (quote → order → delivery → invoice → payment → GL), and multi-entity screens all read across contexts; "no cross-schema join" leaves no read path (the jury's finding) |
| Event spaghetti: flow not visible in code; process managers hard | Fowler [27], Young [29] | Medium: rule 13 (no facade call in an open unit) plus events as the coordination mechanism makes every cross-module invariant eventually consistent |
| Event sourcing everywhere / state beside events | Young [29], Pryce [30], Fowler [28] | Low: the spec chose an append-only journal (§7.9), the right call |
| Too many layers for CRUD | [34] | Medium-high: CRM is mostly CRUD + workflow |
| Building the platform instead of the product | McKinley [41], Fowler YAGNI [14] | **High**: ~30 % of production code is chassis; no UI, no customer, not in production |
| Cell migration cost | Slack [36] | Low if the shard-key invariant holds; do not build cells now |
| Breadth wall: each new entity costs code in many places | Contrast with metadata platforms [24-26] | **High**: no metadata layer, no generated UI/API/report from a model |

## 4. Evaluation of the current architecture against the evidence

Measured on `main` (non-test Python lines): `packages/platform` 17.0k, `countries/do` 15.9k, `modules/signer`
6.5k, `modules/invoicing` 5.8k, `modules/identity` 5.3k, `tools/devtools` 2.8k, `packages/fiscal-kit` 2.0k,
`modules/fiscal` 1.9k, `packages/kernel` 1.8k. No `flows/` package exists yet. The ERP modules (parties, catalog,
accounting) exist only as spec text (§3.2, §7.9).

### Right (keep): the evidence supports these directly
- **Modular monolith, one image, one Postgres** (ADR 0001): matches Shopify, GitHub, Kraken, Basecamp, Fowler,
  Newman [1-17]. ADR 0001's "extract only for a runtime reason" is exactly Shopify's practice [2].
- **Outbox in the producer's transaction, no broker, no Temporal** (ADR 0002, 0003): boring technology [41]; the
  same pattern ships as a framework feature elsewhere [20]. Written revisit triggers are good evolutionary practice [39].
- **Append-only journal with reversals for accounting** (§7.9): matches Helland [32] and Stripe [33], and avoids the
  event-sourcing traps [28-31].
- **Regime/channel split for countries** (ADR 0005): a clean bounded context around what really is the core domain
  [21, 23]; tax law and authority formats vary on different calendars.
- **Signer as the one separate process** (ADR 0010): extraction for a security/legal reason, the only kind
  Shopify extracts for (card vaulting [2]).
- **Shard key invariant and the tax-id registry as the future cell router** (§6.6, ADR 0006): the cheapest possible
  preparation for cells [35]; nothing more is needed now.
- **Fitness functions** (import-linter contracts, `devtools check`, deny-by-default RLS tests, typed strictness):
  the agent feedback loop the evidence recommends [39, 40], and the Kraken pattern [12].

### Over-engineered for a solo founder building breadth
- **Data isolation stricter than any cited monolith.** Per-module schema *and* DML role *and* per-module
  outbox/inbox/jobs tables *and* no cross-schema read, while all modules share one process and one database. Newman
  recommends separated data to keep the split option [17], but the cited companies rarely exercised it (Shopify
  extracted two things [2]; Kraken split integrations [13]). The option is being paid for on every feature and on
  every report. The jury already flagged idle polling that grows per schema.
- **Acyclic graph counting event subscriptions as edges** (rule 2) plus "no facade call in an open unit" (rule 13).
  This turns one database into a distributed-consistency problem. ADR 0011's flows are the first symptom; ERP
  document chains (order → stock reservation → invoice → GL) will produce many more mediators and state machines.
- **Extraction-ready seams for every module** (Protocol + facade + assembly + future gRPC client, §3.9): Fowler and
  Shopify show extraction is rare and expensive anyway; the per-module ceremony is the Shopify "indirection without
  value" failure [2] and the hexagonal-for-CRUD failure [34].
- **Hand-built chassis (~17k lines)** for job queue, eventing, rate limiting, idempotency, dated API versions and
  code generation: undifferentiated infrastructure on which the innovation tokens [41] have been spent before the
  product exists (Fowler's YAGNI and feedback-speed argument [14]).
- **Dated API version pinning before the first client** (ADR 0008) and **test/live mode on every row** (ADR 0007):
  defensible for the e-CF API product; a tax on every ERP table (the jury's data juror said wrong for GL/inventory).

### Missing (what the evidence says breadth requires)
- **A metadata/model layer**: one definition of an entity that generates storage, API, validation, permissions,
  list/form UI, import/export and reports, with per-tenant custom fields. This is the shared trait of Salesforce,
  Frappe and Odoo [24-26] and the main lever for agent productivity on breadth.
- **A read path across contexts**: reporting views or a read replica with published read models (light CQRS [28,
  29]); today the design forbids it.
- **A subdomain map with build/buy calls** [21, 23]: fiscal engine = core (build, which they did); CRM, generic GL
  screens, inventory = supporting/generic (adopt a platform or build on a much thinner, metadata-driven base).
- **A UI architecture** and any end-user surface; no feedback loop from users or production (Fowler [14]).
- **An extension model for tenants and partners** beyond compile-time chained extension points (ADR 0011).

### Verdict on "is it the wrong path?"
The *style* (modular monolith on Postgres) is the right path; the evidence is overwhelming. The *decomposition
granularity and ceremony* are tuned for a multi-team, extraction-ready platform, which is the wrong optimization for
one founder building CRM+ERP breadth with agents. The chassis is a good fiscal-compliance engine; it is not, and
by design does not want to be, an ERP application platform.

---

## 5. Verdict of this angle (5 bullets)

1. **Keep the style:** modular monolith, one Postgres, outbox for side effects, no broker/Temporal, no microservices,
   no cells now (keep only the shard-key invariant). Every cited case (Shopify, GitHub, Kraken, Segment, Istio,
   Prime Video) and every authority (Fowler, Newman, Uber's own advice) supports this for a team of one.
2. **Loosen the decomposition for breadth:** module boundaries should be a ratchet against new coupling (Shopify,
   Kraken), not schema+role+event isolation inside one database. Allow same-transaction cross-module commands and a
   read path (reporting views/replica) for ERP areas; reserve strict isolation (own role, own process) for
   custody and the fiscal core, where law and security justify it.
3. **Breadth needs a metadata-driven application layer**, which is the style Salesforce, Frappe/ERPNext and Odoo
   share and this chassis lacks. Either adopt one (the jury's 5-day Odoo/ERPNext experiment) or build a thin
   model-driven layer; do not hand-write facades, DTOs, events and manifests per CRM/ERP entity.
4. **Use DDD strategically, not tactically everywhere:** the fiscal engine and country packs are the core domain
   (build, deep hexagonal, isolated); CRM, generic GL screens and inventory are supporting/generic (buy/adopt, or
   CRUD on the metadata layer). Accounting is an append-only journal, never event sourcing.
5. **Stop spending innovation tokens on the chassis:** freeze it, keep the fitness functions (they are what keeps
   agent-written code honest), and spend the next effort on the product loop (deploy, a UI, a customer), as
   Fowler's MonolithFirst and McKinley both argue.
