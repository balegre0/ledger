# R8: Folder and code structure (repository layout and module internals)

Research agent R8, 2026-10-25. Scope: how large, long-lived business platforms lay out their repositories and
modules, where country, metadata, UI, generated and test code live, what helps AI coding agents and teams, and
how structure is enforced. Then the current `ledger` repository is checked against that evidence (read-only),
and a target tree is proposed for two scenarios.

**Method and limits.** Web search plus direct fetches of primary pages. Directory facts for Odoo, ERPNext,
Twenty, Business Central and OCA come from the GitHub contents API on the repositories themselves (listings
taken 2026-10-25; they change over time). Some primary pages refused automated fetches. For these I used the
official page's search snippet or a secondary source that quotes it, and say so in the row: OpenAI "Harness
engineering" (HTTP 403), Salesforce DX docs (403), the Google CACM article (403; the research.google abstract was
read instead) and the GitLab modular-monolith design document (the page body was not reachable, so it is not
used). No controlled study comparing package-by-layer with package-by-feature for AI agents was found: **not
found**.

## 2. Findings by theme

### 2.1 Top level: organize by business domain, not by technical layer

- Shopify's Rails code was organized "by software concepts (models, views, controllers)". Shopify reorganized it
  by "real-world concepts (like orders, shipping, inventory, and billing)", with each component "structured as its
  own mini rails app". The goal was "to make it easier to locate code, locate people who understand the code" [2].
  By 2020 the main monolith had 37 components over about 2.8 M lines of Ruby. Every component had initially
  depended on more than half of the others [1].
- Fowler says layering at the top level is "OK for smaller systems". Once a layer grows too big, "you should split
  your top level into domain oriented modules ... which are internally layered" [47]. Martin: the structure
  "should tell readers about the system, not about the frameworks" [45].
- GitLab requires every class to sit in a bounded-context namespace from a registry
  (`config/bounded_contexts.yml`), enforced by a RuboCop cop. It also freezes "omniscient" classes behind a baseline
  that "only gets shorter" [5].
- Every ERP or CRM platform examined uses the business module as its top-level unit, and each module carries a
  self-describing manifest:

  | Platform | Module unit | Manifest |
  |---|---|---|
  | Odoo | addon | `__manifest__.py` [10] |
  | ERPNext | module folder (`accounts`, `buying`, `crm`, `selling`, `stock`, ...) | `hooks.py`, `modules.txt` [18] |
  | Twenty | `src/modules/<object>` (`company`, `opportunity`, `person`, ...) | not listed [27] |
  | Business Central | app folder | `app.json` [32] |
  | Laravel | module | `module.json` [43] |

### 2.2 Inside a module: two families

**Code-centric DDD (per-module hexagonal or clean layering).**
- In kgrzybek's reference implementation, each module is split into Domain, Application, Infrastructure and
  IntegrationEvents, and "only this assembly [IntegrationEvents] can be called by other modules". NetArchTest
  enforces the rules because they cannot be enforced "using compiler" [42].
- Spring Modulith: each direct sub-package of the main package is a module, and its sub-packages are internal [41].
- Cockburn's hexagonal architecture prescribes no folders. It is a dependency rule ("The application is blissfully
  ignorant of the nature of the input device") [46].
- Brown's "missing chapter" argues that clean-architecture diagrams describe dependencies, not folders. He
  recommends package-by-feature or package-by-component over package-by-layer (secondary summary) [48].
- Bogard: "Minimize coupling between slices, and maximize coupling in a slice" [44].

**Metadata-centric platforms (per entity, by artifact kind).**
- **Frappe** colocates everything for one entity in one folder:
  `erpnext/selling/doctype/quotation/{quotation.json, quotation.py, quotation.js, quotation_list.js, test_quotation.py, test_records.json, ...}`
  [16][20]. The JSON defines the DocType and becomes a table, and the metadata is also kept in the database [17].
  This gives the highest change locality of any layout examined: definition, server logic, client logic and test
  sit in one directory.
- **Odoo** organizes by artifact kind, and each file is named after its main model:
  `models/ views/ controllers/ security/ data/ report/ wizard/ static/ tests/ i18n/` plus `__manifest__.py`
  [9][10]. "Each inherited model should be in its own file" [9].
- **Salesforce DX** decomposes metadata into source files. Each custom object gets its own subdirectory under
  `<package-directory>/main/default/objects` [30][31].
- **Business Central (AL)**: one object per file, named `<Name>.<Type>.al`. An extension has `\src` and `\test`
  folders, with extra folders "to group objects based on their functionality" [32].
- **Twenty** keeps a generic metadata engine apart from business objects. `engine/metadata-modules` has 92 entries
  (`object-metadata`, `field-metadata`, `view`, `view-field`, `page-layout`, `role`, `row-level-permission-predicate`,
  `validation-rule`, `workflow`, ...) [26]. Business objects live in `src/modules/<object>/standard-objects` [27].

**What this means for breadth.** In an ERP with hundreds of entities, adding or changing one entity is the most
frequent change. Platforms built for breadth group by entity (Frappe, Salesforce, Twenty) or by entity within an
artifact-kind folder (Odoo). Per-module layer folders (domain/application/adapters) suit modules with few
aggregates and complex rules. This is an inference from the layouts above; no comparative measurement was found.

### 2.3 Country and localization code

- **Kraken.** The layers are `clients` above `territories` above `core`. Clients and territories may not import
  their peers ("independence" contracts), which limits the "blast radius" of a change. Over 40 contracts run on every
  pull request. Known violations were tracked as `ignore_imports` and burned down to 15 [7].
- **Kraken's caveat.** Because higher layers are easier to change, developers wrote client and territory code
  instead of shared core code, and more code ended up in the higher layers than the author wanted [7].
- **Odoo.** Fiscal localizations are installable country modules, installed automatically from the company's
  country. The docs list about 102 countries, Dominican Republic among them [12].
  - Odoo 18 CE ships `l10n_do` as `data/ demo/ i18n/ models/`: a chart and taxes as data, not an e-invoicing
    channel [11].
  - The community `l10n_do_accounting` module (17.0) covers "facturas fiscales dominicanas". Its page does not
    confirm e-CF support [14].
  - OCA splits a country into many small addons at the repository root, one per tax form or bank format
    (`l10n_es_aeat`, `l10n_es_aeat_mod111`, `l10n_es_aeat_mod115`, ...) [13].
- **ERPNext.** In v14, India's regional code moved out of ERPNext into a separate app, India Compliance, which
  "builds on top of ERPNext and the Frappe Framework" [21][22]. The forum described it as part of splitting ERPNext
  into multiple apps [23]. `erpnext/regional` now holds only a few countries (australia, italy, south_africa,
  turkey, united_arab_emirates, united_states) [19].
- **Business Central.** A worldwide base (`W1`) plus per-country layers (`src/Layers/<CC>`: AT, AU, BE, CA, CH, CZ,
  DE, DK, ES, FI, FR, GB, IN, IS, IT, MX, NL, NO, NZ, RU, SE, US, and others) [33].
- **Pattern.** A country is a separately installable unit that depends on core and is never imported by core.
  Heavy countries tend to become their own app or repository (India Compliance, OCA `l10n-*`).

### 2.4 Metadata, UI, shared platform and generated code in the tree

- **Metadata as versioned files beside the module's code.** Frappe DocType JSON [16], Odoo XML views and data
  [9], Salesforce `*-meta.xml` [30] and AL objects [32] all do this. The engine that interprets the metadata sits
  in a platform layer: Frappe itself, Odoo's `base`/`web`, and Twenty's `engine/metadata-modules` [26].
- **UI placement.**
  - Odoo and Frappe ship UI assets inside each module (`static/` [9]; `<doctype>.js` [16]).
  - Twenty is one Nx/Yarn monorepo with `twenty-server`, `twenty-front`, `twenty-ui`, `twenty-shared` and
    `twenty-sdk` side by side in `packages/` [24][29]. The front end is itself split by feature, with 60 entries in
    `twenty-front/src/modules` [28].
  - Turborepo recommends `apps/` for deployables and `packages/` for everything else [39].
  - GitLab keeps EE front-end code in an `ee` folder behind an `ee_else_ce` alias [6].
- **Shared kernel.**
  - Kraken's `core` sits at the bottom [7].
  - Isolating Shopify's base "Platform Essentials" package "took months and required extra tooling" [3].
  - GitLab wants generic `lib/` code moved into `gems/` [5].
  - Polylith keeps bases (entry points) thin: "delegate the business logic to components" [36].
- **Variants and editions.** GitLab keeps all EE code under `ee/`, mirroring CE paths
  (`ee/app/models/ee/user.rb`, tests in `ee/spec/...`), and injects it with `prepend_mod` [6]. This is a proven
  pattern for a "core vs add-on" split inside one repository.
- **Generated code.** Twenty tells agents not to commit translation catalogs except as the task [29]. No primary
  guidance that generalizes was found (**not found**). Common practice: commit generated artifacts that are
  contracts (OpenAPI snapshots, lockfiles), mark them with a header, and check they are not stale.

### 2.5 Tests

- pytest documents two layouts. Tests outside the application code (`tests/`, run against the installed package)
  with a "strongly" recommended `src` layout. Or tests inside the package [65].
- HackSoft: "match the structure of our modules with the structure of their respective tests" [34].
- GitLab mirrors code paths under `ee/spec/` [6]. Frappe colocates `test_<doctype>.py` in the DocType folder [16].
  Odoo uses `tests/` per addon [9][10]. Laravel modules have `tests/{Feature,Unit}` [43]. Cookiecutter Django
  puts `tests.py` in each app [35].
- kgrzybek adds architecture tests (NetArchTest) next to unit, integration and system-integration tests [42].
- **Takeaway.** Tests live per module everywhere. The difference is whether the test tree mirrors the source tree
  (good for discoverability) or splits by test kind.

### 2.6 What helps AI coding agents (and onboarding)

**Small views and immediate feedback.**
- SWE-agent's ablation on SWE-bench Lite (GPT-4 Turbo) [57]:

  | Variant | Score |
  |---|---|
  | 100-line file viewer | 18.0 |
  | 30-line viewer | 14.3 |
  | Whole-file viewer | 12.7 |
  | Edit command with lint feedback | 18.0 |
  | Edit command without lint feedback | 15.0 |

  This measures the agent's interface, not the repository layout. It is indirect evidence that focused, bounded
  views and immediate checks help.
- Anthropic: "Give Claude a way to verify its work" (tests, linters, build exit codes) [52].

**Instruction files: short, nearest-wins, a map rather than a manual.**
- Claude Code loads CLAUDE.md files above the working directory at launch, and "Files in subdirectories load on
  demand" [53]. It can read AGENTS.md [53] and supports path-scoped rules [53].
- Anthropic warns that "Bloated CLAUDE.md files cause Claude to ignore your actual instructions" and that
  file-by-file descriptions of the codebase do not belong there [52] (V).
- AGENTS.md: "The closest AGENTS.md to the edited file wins". The site claims use in "over 60k open-source
  projects" and 88 files in the main OpenAI repo [51] (vendor claims).
- Cursor combines nested AGENTS.md files and advises "Keep rules under 500 lines" [54] (V).
- OpenAI's harness post (403 on fetch) is quoted as "give Codex a map, not a 1,000-page instruction manual", with
  AGENTS.md "as the table of contents" [58][59] (V, read through a secondary source).
- Twenty's CLAUDE.md: match the surrounding code; adjacent files override written rules [29].

**Evidence on context files is mixed.**
- Gloaguen et al. (ETH Zurich according to the search results; the arXiv page does not list affiliations): "context files tend to reduce task success rates compared to
  providing no repository context" and raise inference cost by more than 20%. Recommendation: "human-written
  context files should describe only minimal requirements" [55].
- Lulla et al. (10 repositories, 124 pull requests): with an AGENTS.md, median runtime fell 28.64% and output
  tokens fell 16.58%, with comparable completion [56] (abstract read through a snippet; small sample).
- **Net.** Keep instruction files minimal and specific, and let structure and checks carry the rest.

**Navigation.** Aider ranks files on a dependency graph to build a symbol map within a token budget [60]. A clear
dependency graph and stable public modules (`api.py`, `events.py`) make such maps more useful. This is an
inference.

**Layout and agent success.** No controlled study of folder layout (by layer vs by feature) against agent success
was found: **not found**.

### 2.7 Ownership and Conway's law

- Architectures mirror communication structure. The "Inverse Conway Maneuver" shapes teams to get the
  architecture you want [49].
- Shopify gave every file a stewardship team. Clear ownership made it easier to distribute codebase-wide chores
  and to route exceptions [1].
- GitHub CODEOWNERS requests reviews by path automatically, and branch protection can require owner approval [50].
  GitLab adds CODEOWNERS entries when it freezes omniscient classes [5].
- Google runs one repository for "tens of thousands of developers" (abstract) [67]. Ownership detail was not
  verified from the full text: **not verified**.
- **For a solo founder.** Ownership by module directory costs nothing now and maps directly onto CODEOWNERS when a
  team arrives.

- a separate dev-only `testing/` distribution (fake DGII)
- `tests/{unit,integration,contract/golden}`

**Workspace mechanics.**
- One `manifest.toml` per unit (R-c). Generated `pyproject.toml`, `_manifest.py`, `.importlinter` and
  `openapi.json` (R-e).
- `.importlinter` holds 48 contracts. They include workspace layers, "kernel is stdlib only", platform internal
  layers, and per-package "declared edges". Modules are forbidden to import `ledger_country_do`; countries plug in
  through declared extension points (R-b, R-c).

**Docs and ownership.** 20 READMEs (one per unit). One 35-line root `AGENTS.md` that points to a 2,187-line spec.
No CODEOWNERS file; owners are recorded in each manifest.

### 3.2 Where it matches the evidence

1. **Domain-first top level**, with internally layered modules: exactly Fowler's recommendation [47] and Shopify's
   reorganization [2]. `modules/`, `countries/`, `packages/` and `apps/` read clearly at a glance [45].
2. **Countries as independent units that core may not import.** This matches Kraken's territories [7], Odoo `l10n_*`
   [12], BC country layers [33] and India Compliance [21]. The rule is enforced by generated contracts (R-b), which
   is more rigorous than most of the platforms surveyed.
3. **Thin apps, logic in components.** The five apps total 49 lines, the Polylith "thin base" rule [36]. This also
   follows Turborepo's `apps/` vs `packages/` convention [39].
4. **Manifest per unit plus generated contracts.** This mirrors Odoo `__manifest__.py`, Frappe `hooks.py`, BC
   `app.json` [9][18][32], with mechanical enforcement as at Kraken, GitLab and Shopify [3][5][7].
5. **Agent ergonomics are good at file level.** Small files (median ~82 lines; cf. [57]), a strict machine gate
   (cf. [52]) and a short root AGENTS.md (cf. [52][55]).
6. **Tests per package** in a `src` layout, as pytest recommends [65].

### 3.3 Gaps, judged against the stated goal (a CRM with ERP breadth)

1. **No place for metadata.** There is no directory or engine for declarative objects, fields, views, list and
   form layouts, reports or print formats. Every breadth platform has one: Frappe DocType JSON, Odoo XML,
   Salesforce `-meta.xml`, Twenty `metadata-modules` [16][9][30][26]. `manifest.toml` is module-level metadata
   (permissions, events, ids), not entity-level or UI-level.
2. **Low per-entity change locality inside modules.** Adding one entity to `invoicing` touches
   `domain/<entity>.py`, `application/{commands,queries,facade}.py`, `adapters/postgres/{tables,repositories}.py`,
   `adapters/http/{models,<entity>}.py`, `migrations/versions/`, plus `tests/unit` and `tests/integration`. That is
   about 6 directories and 8 or more files. Frappe needs one folder [20].
   - **Drift.** The spec says `repositories/<aggregate>.py` (R-d §4.1), but invoicing and identity each have a
     single 700–800-line `repositories.py`. That will grow with every entity.
   - **Fit by module.** The layered hexagon fits deep modules such as `fiscal`, `signer` and the DR channel. It will
     not scale gracefully to breadth modules such as CRM, inventory and purchasing.
3. **No UI or report location.**
   - The uv workspace takes members by glob (`apps/*`, R-e). A TypeScript app dropped into `apps/web` would break
     sync and check unless excluded. uv supports `exclude` [66], but devtools and the manifest schema
     (`kind = module|country|app|package|tool`) have no `web` kind.
   - There is no report engine package and no `reports/` convention (BACKLOG territory).
4. **The chassis is the largest unit.** `packages/platform` (17k lines, 99 files) is what Odoo, Frappe and Twenty
   provide as their framework [26]. Shopify's experience is that isolating the base layer is costly even with
   tooling [3]. This is a scope gap, not a layout fault, but it is where the tree "screams" infrastructure rather
   than business [45].
5. **Tests split by kind rather than mirroring the source.** `tests/unit/test_invoice.py` versus
   `src/.../domain/invoice.py` works by naming convention, but there is no path mirror (cf. [34][6]). At 30 modules
   this costs discoverability for humans and agents.
6. **The spec is a 2,187-line single document** and is the source of truth. That is the "manual" OpenAI's team
   moved away from [58][59], and Anthropic advises loading domain knowledge on demand [52].
   - Per-module READMEs exist, which is good.
   - The countervailing evidence [55] argues against adding many AGENTS.md files. A short one only where a
     directory has non-standard rules is the defensible middle.
7. **No CODEOWNERS yet.** Fine solo. Owners are already in the manifests, so it can be generated later (R-e lists
   this as deferred) [50].
8. **Minor.** The spec lists a root `tests/` for whole-repo invariants (R-d §4.1). It does not exist; whole-repo
   checks live in `tools/devtools/tests/workspace`.

**Overall.** The layout is a textbook, well-enforced modular-monolith layout for a fiscal engine. Its gaps are the
missing breadth layers (metadata, UI, reports) and an inside-module pattern tuned for depth, not breadth.

## 4. Recommended target trees

Conventions for both scenarios: `apps/` = deployables, `packages/` = libraries, both language-agnostic, after
Turborepo [39] and Twenty [24]. One manifest per unit. Generated files carry a header and are checked for
staleness. Short AGENTS.md files only where rules differ.

### 4b. Scenario B: take breadth from Odoo or Frappe; the current code becomes a fiscal-engine service beside it

- Odoo and OCA: one repository per topic, addons at the root, branches per Odoo version [13].

Why two repositories, not one monorepo, in B:
- **Different release clocks.** Odoo and OCA branch per version; the engine is trunk-based.
- **Different toolchains and gates.** The Odoo/Frappe test runners do not fit this repository's 100% branch,
  strict-typing gate.
- **A real external contract.** The engine is meant to be sold to other software vendors too, so the seam must be
  an external contract anyway.
- **The cost:** no atomic cross-repository change [67]. It is mitigated by dated API versions and contract tests
  on both sides.

These are judgments drawn from [13][21][58]; licensing implications of the ERP side are out of R8's scope.

## 5. Verdict

- **The repository layout is not the wrong path. It is above the median of the platforms surveyed.** It has a
  domain-first top level [2][47], countries isolated from core by generated contracts like Kraken's
  territories [7], thin apps [36], a manifest per unit like Odoo, Frappe and BC [9][18][32], small files and a hard
  gate [52][57]. Keep it in either scenario.
- **What is missing for "CRM with ERP features" is three layers, not a re-layout:**
  - a metadata engine plus per-module `metadata/` definitions (every breadth platform has one [16][26][30]);
  - a UI app and UI library under `apps/` and `packages/` [24][39];
  - a report and print engine.

  All three slot into the existing tree, with uv `exclude` and a new manifest `kind` for the TypeScript units [66].
- **Change the inside of breadth modules from layer folders to entity slices** (`quotes/`, `sales_orders/`, each
  with domain, commands, queries, repository and http), with tests mirroring them. Keep the layered hexagon for deep
  modules such as fiscal, signer and the DR channel. Fix the single 800-line `repositories.py` drift now
  [20][44][48] (R-d).
- **For agents, prefer structure and checks over prose.**
  - Split the 2,187-line spec into an indexed set ("a map, not a manual" [58][59]).
  - Add a short AGENTS.md only where a directory's rules differ ([51][53]; evidence warns that long context files
    cost more than 20% extra and can lower success [55]).
  - Generate CODEOWNERS from the manifests when a second person joins [50].
- **If scenario B wins** (breadth from Odoo or Frappe), this repository becomes `ledger-engine` almost unchanged.
  The ERP side lives in its own repository and follows its platform's conventions exactly: an OCA addon-per-
  directory repository [13], or a separate Frappe app like India Compliance [21]. A thin connector calls the
  engine's generated client. In both scenarios a country pack stays an independently installable unit that core
  never imports [7][12][21][33].
