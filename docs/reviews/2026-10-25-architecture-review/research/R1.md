## 2. Cross-cutting patterns the winners share

**P1. The data model is metadata, and the platform's own objects use the same mechanism as customer objects.**
Salesforce (objects/fields as rows in the Universal Data Dictionary, kernel interprets them [1][2]); Workday
("millions of metadata definitions", structure change without DB restructuring [24][25]); Dataverse (tables,
messages, plug-in steps all stored as rows [9]); Frappe (a DocType is itself a DocType [39]); Twenty (standard
objects go through the same metadata pipeline as custom ones [43]); HubSpot (custom objects on the same
infrastructure as standard objects [31]); Oracle Fusion (Application Composer, flexfields [19][20]); ServiceNow
(single data model across products [28]). This is the single most consistent finding: **every product in scope
that is sold as a configurable CRM/ERP has a metadata layer; none has a fixed, compile-time-only schema.** The
exception that proves it is Odoo, whose model is Python code — but even Odoo builds its model registry per
database at runtime from installed modules and exposes Studio/custom fields on top [35].

**P2. Metadata is the source of UI, API, reports and permissions, not just storage.** Frappe generates list,
form and report views from DocTypes [39]; Twenty generates per-workspace GraphQL/REST/MCP from metadata [42][43];
Workday's runtime turns definitions into tasks and reports [25]; Salesforce's kernel delivers tenant-specific
apps and APIs [1]. The leverage is that one definition yields screens, endpoints, filters, reports, import/export
and field-level security. A product without this writes each of those by hand per object, per country.

**P3. Physical storage of metadata-defined data has converged on "real typed columns when DDL is cheap".**
Salesforce's flex columns + pivot index tables [1] are a 1999 answer to "one shared Oracle schema, no per-tenant
DDL". Newer systems instead run real DDL: Frappe/ERPNext creates a table per DocType [39]; Twenty diffs
metadata and runs DDL into a per-workspace Postgres schema [43]; Workday persists to a relational store but
serves from memory [24]. Generic EAV/JSON-only designs are a known trap at scale [48][49]. Lesson: a Postgres
newcomer does not need Salesforce's UDD; it needs a metadata catalogue + a migration runner that emits typed DDL,
with JSON only for genuinely sparse attributes.

**P4. One codeline, everyone on (nearly) the same version.** Salesforce (single kernel, Hyperforce as an infra
move not a fork [1][4]); Workday (3 updates/year to all [24], single version [26]); NetSuite (single
instance, all customers same version, 2 major upgrades/year [22]); Frappe public benches run the same app version
for many sites [41]. Even ServiceNow, which is multi-instance, keeps customers "within a release or two" and
pays for it in version sprawl [30]. Tenancy topology varies (shared schema, schema-per-tenant, DB-per-tenant,
instance-per-customer) — **the codeline does not.**

**P5. Extensions run through a governed, versioned contract, never by editing the core.** SAP's clean core
Levels A–D, rating an extension by its lowest technique and pushing to released APIs or side-by-side on BTP
[13][14][15]; Dataverse's message pipeline with stages, 2-minute/CPU/memory caps and a sandbox [9][10];
Salesforce governor limits [3] and namespaced, upgradeable managed packages [6]; NetSuite usage units [21];
Frappe hooks with explicit override/extend semantics [40]; Workday Extend building on the object/security
model without touching delivered code [27]. Governance limits are not an accident — they are what makes a
shared runtime safe to open to third-party code.

**P6. A layered extension ladder: configuration → declarative automation → sandboxed code → side-by-side apps.**
Every major platform offers the same ladder: fields/objects/layouts (Application Composer, Customize Form,
Salesforce Setup), no-code workflow on the same event bus as code (Dataverse workflows use the event framework
[9]), server-side code in a governed runtime (Apex, plug-ins, SuiteScript, Frappe hooks), and external apps via
API/events (BTP side-by-side [13], Workday Extend [27], Twenty apps SDK [43]).

**P7. Packaging and lifecycle for customizations.** Dataverse solutions with managed/unmanaged layers and "top
wins" merge [11]; Salesforce 2GP packages with version control as source of truth [6]; Frappe fixtures synced from
JSON [40]. Configuration is treated as deployable, versioned artifacts — which is exactly what the owner's
manifest-driven devtools already does for code, but not for tenant configuration.

**P8. Platform + marketplace is the moat, and it is built on P1–P7.** AppExchange (managed packages [6]),
Dataverse solutions [11], Odoo Apps/OCA modules [37], Frappe apps [40][41], Workday Extend [27], Twenty apps
[43]. The marketplace is only possible because the platform has a stable metadata contract and isolated extension
points.

**P9. ERP core uses a single line-item ledger, not per-module totals.** SAP's Universal Journal (ACDOCA) puts
FI, CO, assets and material postings in one table with all dimensions, removing reconciliation [17][18]. This
is the strongest data-model lesson for the "ERP features" half of the product.

**P10. Big monoliths are normal; services are split out for specific reasons.** Salesforce Core is a monolithic
Java codebase [5]; Shopify runs a 2.8M-line modular monolith and splits services only "for good reasons" [47];
Odoo and Frappe are Python monoliths. HubSpot [32] and Pipedrive [46] moved to microservices as their
*engineering organizations* grew, not as a starting architecture.

## 3. Failure modes and costs reported

1. **Customization sprawl / org debt (Salesforce).** Because adding a field or automation is easy, orgs
   accumulate overlapping automations, hundreds of fields on core objects, and permission tangles that make
   simple changes take weeks [7][8]. The metadata layer moves complexity from vendor code to customer config.
2. **Governor limits as a developer tax.** Code that is fine at 100 records fails at 1,000 [7]; Dataverse kills
   plug-ins over CPU/memory and rolls back at 2 minutes [10]; NetSuite meters every API call in usage units
   [21]. Necessary for shared runtimes, but every extension author must design around them.
3. **Upgrade breakage from in-place extension (Odoo).** Odoo's `_inherit` in-place extension and "later
   definition silently overwrites" semantics [35] mean custom and third-party modules must be ported every
   version; partners price this per module or per 1,000 LOC [37][38]. This is the cost of "extension = editing
   the model class" without SAP-style released-API discipline.
4. **Mandatory upgrades vs customizations (NetSuite).** Single-version multitenancy forces biannual upgrades that
   put customer SuiteScript at risk [23].
5. **Unmanaged configuration drift (Dataverse).** Ad-hoc changes in production override packaged behavior and
   break upgrades [12].
6. **Version sprawl (multi-instance).** ServiceNow's per-customer instances cost repeated upgrade work and
   multiple supported versions [30]; the same risk applies to any "DB per tenant" design that lets tenants lag.
7. **Clean-core debt (SAP).** SAP needed a multi-year program (tiers → Levels A–D, ATC checks, changelog of
   internal objects) to undo decades of customers modifying the core [13][14]. Retrofitting extension discipline
   is far more expensive than designing it in.
8. **Generic storage performance.** EAV/JSON-everything collapses on large tenants via skewed planner statistics
   and many self-joins [48][49]; Salesforce needed bespoke pivot index tables and its own optimizer to make flex
   columns work [1].
9. **Monolith onboarding cost.** Salesforce Core takes "months of onboarding" [5]; Shopify found strict interface
   rules added friction and refactors stall half-done [47].
10. **Premature microservices.** Shopify warns splitting "increases the overall complexity considerably" [47];
    HubSpot/Pipedrive's service fleets [32][46] exist to serve hundreds of engineers, a problem a solo founder does
    not have.

## 4. What this implies for the owner's question

### Is "a custom Python modular monolith with no metadata layer" the wrong path?

Split the claim into its three parts:

- **"Python"** — not wrong. Odoo and Frappe/ERPNext, the two most successful open-source ERPs, are Python
  monoliths on Postgres/MariaDB [35][39][41]. Language is not where incumbents differ.
- **"Modular monolith"** — not wrong; it is what the incumbents actually are. Salesforce Core is a monolith [5];
  Shopify's is 2.8M lines [47]; microservices came later and for org-scale reasons [32][46].
- **"No metadata layer"** — **this is the part that is wrong for a sellable CRM-with-ERP.** Every product in
  this survey that customers configure has one (P1), and it is what produces UI, API, reports and permissions
  from one definition (P2), what makes custom objects/fields possible without a release, and what a
  marketplace stands on (P8). A fixed, compile-time schema with compile-time-only extensions is the architecture
  of a *vertical engine* or a *bespoke system*, not of a CRM platform. The incumbents' history also says this
  layer is very expensive to retrofit (SAP's clean-core program [13][14]; Odoo's upgrade tax [37]).

So: the current repo is a strong **fiscal/e-CF engine** (signer isolation, outbox, idempotency, RLS, legal
archive) — capabilities incumbents also have, but that are not what makes them sellable as CRM/ERP. It is the
wrong *starting chassis* for CRM/ERP breadth unless a metadata layer is added; and building that layer
(catalogue, DDL migration runner, generated API, generated UI, report engine, field-level permissions,
workflow engine, packaging) is itself a multi-year platform effort that Odoo, Frappe and Twenty have already
done in open source. This agrees with the earlier jury's conclusion recorded in CONTEXT.md, now with the
incumbent evidence behind it.

### Minimum architectural capabilities for a sellable CRM-with-ERP (derived from what every incumbent ships)

1. **Metadata-driven data model**: objects, fields (typed), relations, picklists, validation rules, numbering,
   stored as data, versioned, with a migration runner that emits typed DDL (Twenty/Frappe style [39][43]);
   standard objects defined through the same mechanism as custom ones.
2. **Generated surfaces from metadata**: CRUD REST/GraphQL API, list/kanban/form views, search, import/export,
   webhooks — for every object, standard or custom [39][42][43].
3. **Permission model at object, field and record level** (roles, sharing/ownership, teams, multi-company),
   enforced by the platform, not per endpoint [1][5][40].
4. **Event pipeline + workflow engine**: before/after-save hooks in-transaction and async, plus a no-code
   workflow/approval builder on the *same* event bus [9][40].
5. **Governed extension runtime**: sandboxed or limited server-side code with time/CPU/query budgets
   [3][10][21], and a released-API contract that extensions must use (SAP Level A discipline [13]).
6. **Packaging/ALM for configuration**: tenant customizations and partner apps as versioned, namespaced,
   upgradeable packages with layering rules [6][11][40].
7. **Reporting/analytics** over metadata: report builder, dashboards, and an accounting-grade ledger that is a
   single line-item journal with dimensions [17][18].
8. **Single codeline multitenancy** with a chosen isolation unit (shared schema + RLS, schema-per-tenant as in
   Twenty, or DB-per-tenant as in Odoo/Frappe) and everyone on one version [4][22][30][41].
9. **Localization as a pluggable layer** (tax, e-invoicing, chart of accounts, numbering per country) — Odoo's
   `l10n_*` modules and SAP's country versions are the pattern; the owner's `countries/do` package is already
   this shape and is the most reusable part of the repo.
10. **Public API + integration surface** (webhooks, OAuth apps) that external apps can build on side-by-side
    [13][27][31].

Items 8–10 the current repo partially has (RLS tenancy, `countries/do`, API-first). Items 1–7 it does not.

### Practical options this angle suggests (for the synthesizer, not a final ruling)

- **Build on an existing metadata platform** (Odoo CE/Enterprise, Frappe/ERPNext, or Twenty for the CRM half)
  and port the DR e-CF engine into it as a localization app — the "clean core + side-by-side" pattern, with the
  current signer/receiver kept as an isolated side-by-side service [13].
- **Keep the repo as a side-by-side compliance service** (e-CF issuance, signing, DGII channel, legal archive)
  sold via API to other software vendors and plugged into whichever CRM/ERP platform is chosen.
- **Build the metadata layer yourself** only if the founder is willing to spend most of the next year on
  platform work before CRM/ERP features; Twenty's design (metadata tables → DDL into per-workspace Postgres
  schema → generated API) is the cleanest modern blueprint, but Twenty is TypeScript/AGPL [43][44].

---

## 5. Verdict (this angle)

- **Every incumbent sold as a configurable CRM/ERP is metadata-driven** (Salesforce UDD, Dataverse, Workday object
  model, Frappe DocTypes, Twenty, HubSpot custom objects, Fusion Application Composer); a fixed compile-time schema
  is the architecture of an engine, not of a CRM/ERP platform.
- **The "modular monolith in Python on Postgres" part is not the mistake** — Salesforce Core, Shopify, Odoo and
  Frappe are monoliths, and Odoo/Frappe are Python; microservices appeared at HubSpot/Pipedrive for org-scale
  reasons a solo founder does not have.
- **The missing pieces are platform capabilities, not code quality**: metadata catalogue + DDL migration runner,
  generated API/UI/reports, object/field/record permissions, event pipeline + no-code workflows, a governed
  extension runtime with released APIs, and packaged configuration — all of which Odoo, Frappe and Twenty already
  ship in open source.
- **Incumbents' scars say design extension discipline in from day one**: SAP's clean-core retrofit, Odoo's
  per-version module porting, Salesforce org debt and governor-limit pain show that "extend by editing the model"
  and ungoverned customization are the expensive failure modes.
- **For this founder the incumbent pattern points to "clean core + side-by-side"**: keep the e-CF/fiscal engine as
  an isolated, API-first compliance service (its real moat) and get CRM/ERP breadth from an existing metadata
  platform rather than rebuilding Salesforce's kernel; building one's own metadata layer is defensible only as
  an explicit, year-scale platform bet.
