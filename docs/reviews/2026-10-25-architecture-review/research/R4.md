# R4: Extensibility and platform design for business apps

Researcher R4 of 7. Angle: metadata-driven platforms, customization tiers, plugin isolation, workflow engines,
API-first design, and what customization costs at upgrade time.
Method: WebSearch in standard mode, WebFetch on primary pages, and a read-only look at the repo (ADR 0003, ADR 0009,
ADR 0011, spec §3.10, §9.3 and §9.9, jury synthesis §5).

of the ERPNext/Odoo codebases, Twenty's funding and team, and the count of Odoo app-store/OCA modules. Those are
marked "not found". No numbers below are invented. Vendor claims and anecdotes are labelled as such.

## 2. The extensibility model a sellable CRM-with-ERP needs

The tiers below follow the industry split into configuration, low-code and pro-code: SAP's key-user, developer
and side-by-side extensibility [11]; Dataverse's managed and unmanaged layers [26]; Frappe's Customize Form versus
apps [4][5].

### At launch (first DR SMB tenants, one founder)

| Tier | What buyers expect | Who uses it | Isolation |
|---|---|---|---|
| T0 Configuration | Company settings, tax and numbering setup, chart-of-accounts template, users and roles, currencies, print/PDF templates for quotes and invoices (logo, footer, fields shown), email templates | Tenant admin | Data only |
| T1 Light customization (metadata as data) | **Custom fields** on the core CRM/ERP records (customer, contact, deal, product, quote, invoice): typed, validated, filterable, exportable, shown on forms and in reports. **Configurable pipelines and stages**, picklists and tags, saved views and filters | Tenant admin, no code | Data only. Typed core columns plus JSONB for custom values [32]. No per-tenant DDL, no EAV |
| T2 Automation rules | "When a deal reaches Won, create a quote; when an invoice is overdue, send an email, create a task or fire a webhook". A small declarative trigger, condition and action set over the domain events that already exist | Tenant admin | Runs on the existing job queue. **Not** BPMN, **not** Temporal [27][28] |
| T3 Integration (out of process) | Public REST API with versioning, API keys/OAuth, webhooks, idempotency, CSV import/export, and connectors to the 3-5 local systems that matter (bank, POS, e-commerce) | The customer's developers, integrators | Total: their code runs on their servers (the Shopify/Stripe model [15][22][24]) |
| T4 Pro-code | First-party modules and country packs, written by the founder (and the agents) | Vendor only | Compile time, reviewed, behind the full gate |

Not needed at launch: a marketplace, third-party in-process code, custom **objects**, a visual workflow builder,
BPMN, Temporal, a UI-extension SDK, a unified-API product. Elements.cloud's data says 51 % of custom objects are
never used [14]: custom objects are the most expensive tier and the least used, so they can wait.

### At scale (hundreds or thousands of tenants, partners, several countries)

- **Metadata as code for partners.** Versioned, namespaced extension packages that are installed per tenant and
  layer over core without forking it, can be upgraded and uninstalled, and may only use released APIs. Examples:
  Salesforce 2GP [12], Dataverse managed solutions [26], Twenty apps [3], HubSpot projects [30], SAP's "released
  APIs only" rule [11].
- **Out-of-process apps as the main marketplace model.** OAuth apps, webhooks, and UI slots rendered in sandboxed
  iframes with short-lived session tokens (Shopify App Bridge [15], HubSpot app cards [30]), with a review gate
  before an app can be listed or push-upgraded [12].
- **Sandboxed synchronous hooks** for the few places where latency rules out a webhook (pricing, discount and
  validation hooks). Use WASM with an instruction or time budget (Shopify Functions, 11M instructions [17]; Extism
  in a Python host [20]; Figma's swappable membrane [18]) or buy hosted isolation (Cloudflare Workers for Platforms
  [21]). Never in-process interpreted plug-ins with database access.
- **Custom objects**, generated APIs and a metadata cache (the Salesforce UDD [1] or Twenty's metadata engine [2]),
  only once demand is proven.
- **A workflow engine** only when long-running cross-module sagas with compensation multiply. The repo's ADR 0003
  triggers say exactly that.
- **Unified-API connectors** (Merge-style common models plus a passthrough [25]) if the product becomes a hub that
  integrates many third-party systems. Buy before build ([25]: $156k/yr at 200 accounts is a competitor's claim).

## 3. Build on a framework, or build your own metadata layer

| Dimension | Framework (Odoo / Frappe-ERPNext; Twenty for CRM) | Own metadata layer on the current chassis |
|---|---|---|
| What you get on day 1 | Metadata engine, custom fields (Frappe Custom Field/Property Setter [4]; Odoo Studio, `_inherit`, view `xpath` [6]), generated forms, list views, reports, print formats, permissions UI. Twenty: custom objects plus generated GraphQL [2] | Nothing at the metadata/UI tier. The chassis has none (jury §5). You build the field-definition store, validation, the form/list renderer, report and print templates, and import/export |
| How big a metadata engine is | Not measured this session: ERPNext/Odoo line counts were not found (search budget). Proxy: Twenty, a CRM-only metadata engine, has 17,388 commits [3] | Salesforce's fully general engine needs flex columns, 5+ pivot tables, a metadata cache, a custom query optimizer, and partitioning [1]. That is multi-year, large-team work. **A narrow layer** (custom fields, picklists, pipelines, saved views on fixed objects) is a far smaller problem: typed core columns plus JSONB plus a field-definition table plus promoted expression indexes [32]. No public number was found for its size |
| Third-party code trust model | In-process Python with full ORM/database access (Odoo modules, Frappe apps and server scripts [4][5]). One app overriding a DocType class beats another (secondary source [5]). Odoo Online bans custom Python modules entirely [7]: Odoo's own SaaS cannot trust them | Your choice. The out-of-process plus WASM model [15][17][20] is open to you, and it also protects the custody/RLS design |
| Upgrade tax of customization | Odoo: custom modules sit outside the standard upgrade and must be ported per version [7]. Partners quote ~75 % of the original customization cost per migration [8] and ≥50-70 h even with zero customizations [9] (vendor claims) | Clean core by design (SAP's lesson [11]): if tenants customize only through data (T0-T2) and released APIs (T3), core upgrades never break them. Salesforce shows the opposite: 31 % high tech debt, 2 % clean orgs [13], 51 % unused custom objects [14] |
| Tenancy | Odoo: database per tenant. ERPNext: site per tenant (jury §5). Tenancy is enforced in the ORM | Postgres RLS on tenant/company/mode, already built and tested |
| Licensing to resell | Not verified this session (left to the build-vs-buy researchers). n8n shows that "source-available" licences can block embedding [29] | Yours |
| Fit for a solo founder plus agents | Breadth arrives fast. Agents write Odoo/Frappe code that cannot reach the repo's quality bar (in-process, untyped hooks, no RLS) | Quality stays high, but the missing tier (UI plus metadata) is the expensive half of a CRM/ERP, and nobody has started it |

What these numbers mean:
- Frameworks swap a large up-front cost (the metadata and UI tier) for a recurring cost (upgrade tax and an
  in-process trust model).
- Building your own reverses that trade.
- The reverse is affordable only if the metadata layer stays **narrow**: fields, picklists, pipelines, views and
  templates on a fixed set of first-party objects. Never a generic custom-object engine at launch.

## 4. How the current design fits

**What fits well (keep it):**
- **The integration tier (T3) is at best-practice level already.**
  - Dated API versions with the Stripe cadence and planned version-change transforms (spec §9.2; [22][23]).
  - Standard Webhooks with **thin** payloads, `whsec_` secrets, signed per attempt (spec §9.9; [24]).
  - Idempotency keys, test and live modes, TypeIDs, RFC 9457 errors.
  - This is the Stripe/Shopify model, in which third parties extend you **out of process**, the safest model
    there is [15][19].
- **Manifests are metadata-as-code for first-party code** (ADR 0009). They already declare schemas,
  permissions, events and their public names, jobs, extension points and settings, and they generate contracts,
  grants and OpenAPI. They are a good foundation for a partner-package format later, close to Salesforce 2GP [12],
  Dataverse solutions [26] and Twenty apps [3].
- **Chained, ordered, typed extension points (ADR 0011)** are a disciplined version of Odoo's `_inherit`/`super()`
  chains and Frappe's `doc_events` [5][6]. A declared `(order, module)` ordering and Protocol-defined result
  combination avoid Frappe's "last installed app wins" conflict [5]. Flows as acyclic leaves keep the core
  extractable.
- **ADR 0003 (no Temporal yet)** matches the evidence: database-persisted state machines on a job queue until
  sagas with compensation multiply [27][28].
- **Clean core by construction.** No customer code runs in the core process. That is exactly what SAP is now
  trying to restore [11], and what Odoo Online enforces by banning custom Python [7].

**What does not fit a sellable CRM-with-ERP (gaps):**
1. **No runtime, per-tenant customization tier (T0/T1/T2 are missing).**
   - Every extension point is **compile-time**: resolved at assembly from installed packages, the same for all
     tenants (spec §3.10). A tenant cannot add a field, a pipeline stage or an automation rule without a release.
   - The only per-record flexibility is Stripe-style `metadata` (spec §9.3): ≤ 50 string keys, "never indexed",
     no PII. That is right for integrator tags. As CRM custom fields it fails: no types, no filtering, no
     reporting, no UI.
2. **No UI, so no UI extension slots, form layouts or print templates.** For an SMB CRM/ERP buyer the UI *is* the
   customization surface (Customize Form [4], Odoo view inheritance [6], HubSpot app cards [30]).
3. **No per-tenant install and no packaging boundary for third parties.**
   - Extension points are Python Protocols inside one monolith, behind a 100 % coverage, zero-suppression gate.
     No partner can ship into that, and should not: that is the right call for trust.
   - It does mean the only partner extensibility is the API plus webhooks. That is enough at launch and too
     little for a marketplace at scale (no UI slots, no synchronous sandboxed hooks).
4. **The manifest model describes packages, not business entities.** It lists no entity or field descriptors. So
   nothing exists yet that a metadata-driven form, list or report layer could be generated from, the way
   Twenty generates GraphQL from Object/Field metadata [2] or Directus generates APIs from a schema [31].

**Net:** the current design gets the **hard-to-retrofit** parts of extensibility right:
- out-of-process integration;
- versioned contracts;
- a clean core;
- typed first-party extension points;
- isolation that a framework cannot give (in-process modules with full database access).

It is missing the **expensive-to-build, must-have-at-launch** parts: tenant-level configuration and custom
fields, automation rules, UI and templates. That is not a wrong path. It is an engine without the application
tier, as the jury already said. The question is whether that tier gets built (narrowly) or bought (a framework
put in front of the engine).

## 5. Verdict

- **The current extensibility design is right for an engine and incomplete for a CRM/ERP product.** API
  versioning, Standard Webhooks, a clean core and typed, ordered compile-time extension points (ADR 0009/0011)
  match Stripe, Shopify and SAP clean-core best practice and are hard to retrofit. Keep them. What is missing is
  the whole tenant-facing customization tier.
- **At launch, sell configuration rather than a platform.** Ship tenant settings, typed custom fields on the core
  records (typed columns plus JSONB, not EAV and not per-tenant DDL), configurable pipelines, print/email
  templates, a small trigger-condition-action rule engine on the existing job queue, and API plus webhooks. Do not
  ship a marketplace, custom objects, BPMN or Temporal at launch: 51 % of Salesforce custom objects go unused, and
  ADR 0003 still holds.
- **Never run third-party code in-process.** At scale, extend out of process (OAuth apps, webhooks, iframe UI
  slots with session tokens, a review gate) and run synchronous hooks in a budgeted WASM sandbox: Shopify
  Functions, Extism in Python, or Cloudflare Workers for Platforms. This keeps the core clean and avoids the
  Odoo/Salesforce upgrade tax (partners quote ~75 % of the customization cost per Odoo migration; 31 % of
  Salesforce orgs carry high debt and 2 % are clean).
- **Build or buy depends on the UI and metadata tier, not the backend.** Odoo, Frappe or Twenty give metadata,
  forms, reports and custom fields on day 1, in exchange for an in-process trust model, ORM-level tenancy and a
  recurring upgrade tax. Building it yourself is viable only if it stays narrow (fields, pipelines, views and
  templates on fixed first-party objects). A Salesforce/Twenty-style generic engine is multi-year work (Twenty:
  ~17k commits) and out of reach for a solo founder.
- **Next step: give the jury's 5-day experiment an extensibility checklist.** Measure:
  - the cost of adding a custom field, a pipeline stage and a print template in each option;
  - whether third-party code can be kept out of process;
  - the upgrade path for one customized module.

  If the platform route is chosen, extend the manifests with entity/field descriptors so that forms, OpenAPI and
  reports can be generated from one source.
