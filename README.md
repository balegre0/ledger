# ledger

A business platform sold as an API, starting with Dominican Republic electronic invoicing (e-CF). It is a modular
monolith: modules and country packs composed into a few apps that share one chassis and one PostgreSQL. The design
is [docs/superpowers/specs/2026-10-13-ledger-platform-v2-design.md](docs/superpowers/specs/2026-10-13-ledger-platform-v2-design.md).

Python 3.15 · uv workspace · strictly typed in two checkers · zero suppressions · 100 % branch coverage per package.

## Layout

| Path | What |
|---|---|
| `packages/` | `kernel` (the shared vocabulary, standard library only), `platform` (the chassis), `fiscal-kit` (the contract between fiscal and its channels: drafts, statuses, the signer port, hardened XML), `testing` (test tooling, dev-only) |
| `modules/` | Business modules, each in its own PostgreSQL schema and role: `identity`, `invoicing`, `fiscal` (enrollments, routing documents to fiscal channels, their status mirror), `signer` |
| `countries/` | Country packs: `do` (regime `do`, the e-CF channel `do-ecf-v1`) and its dev-only `do/testing` (a fake DGII) |
| `apps/` | The deployables: `api`, `worker`, `receiver` (the tax authority's and other emitters' calls), `signer`, `migrate`; they compose the installed modules and hold no business code |
| `contracts/` | Wire contracts (buf); protos arrive with the signer |
| `tools/devtools` | `ledger-devtools`: checks the manifests and generates what follows from them |
| `deploy/` | The image (`docker/ledger.Dockerfile`) and the local stack (`local/`) |

Every package has a `manifest.toml`, the source of truth for its dependencies, layers and generated files.

## Develop

You need [uv](https://docs.astral.sh/uv/) 0.13 or later (it installs CPython 3.15) and a running Docker: the tests
start a real PostgreSQL.

```bash
uv sync --all-packages   # every package of the workspace into .venv (the root itself depends on nothing)
uv run poe check         # the gate, as CI runs it
uv run poe fmt           # format and autofix
uv run poe sync          # after editing a manifest: rewrite what it implies, then commit the result
uv run poe               # every task
```

What `ledger-devtools sync` writes is never edited by hand: each `pyproject.toml` but the root's, `_manifest.py`,
identity's role table (`domain/_role_grants.py`, from every manifest's permissions), `.importlinter` and
`deploy/local/postgres/init.sql` (each headed `GENERATED by ledger-devtools sync`), each
module's `openapi.json`, and the root `pyproject.toml`'s block between its two `ledger-devtools sync` marker lines
(every list there that names packages). Adding a package touches only its directory and generated files.
`LEDGER_TEST_JOBS` caps how many packages test at once. On Windows, pytest-timeout (thread mode) ends a hung test
with `os._exit`, which xdist reports as `node down`: look for the `+++ Timeout +++` dump above it before blaming
the machine's load, and lower `LEDGER_TEST_JOBS` when several gates share one machine.

## The gate

`uv run poe check`: ruff format and ruff with every rule, no suppression comment anywhere, basedpyright (`all`)
and mypy `--strict`, import-linter, deptry, typos, buf, `ledger-devtools check` (manifests valid, generated files
current, image pins equal to `deploy/local/images.toml` and carrying digests, `.dockerignore` keeping
secrets out of the build context), vulture, and each package's tests with 100 % branch
coverage and warnings as errors. CI (`.github/workflows/ci.yml`) runs the same, then builds the image and starts
the local stack from it.

## Run locally

```bash
sh deploy/local/signer/tokens.sh                                    # once: the signer's callers' tokens (git ignores them)
sh deploy/local/do/roots.sh                                         # once: do-ecf-v1's development root (worker, receiver)
docker compose -f deploy/local/compose.yaml up -d --build --wait   # postgres, migrate, api, worker, receiver, signer, fake DGII
docker compose -f deploy/local/compose.yaml down -v                 # stop and delete the data (and the signer's KMS key)
```

| | Host address |
|---|---|
| api | `http://127.0.0.1:8100` (`LEDGER_API_PORT`) |
| worker (probes, metrics) | `http://127.0.0.1:8101` (`LEDGER_WORKER_PORT`) |
| signer (probes, metrics) | `http://127.0.0.1:8102` (`LEDGER_SIGNER_PORT`) |
| receiver (the tax authority's and other emitters' calls) | `http://127.0.0.1:8103` (`LEDGER_RECEIVER_PORT`) |
| fake DGII (dev only: DGII's services and a buyer's receiver) | `http://127.0.0.1:8471` (`LEDGER_FAKE_DGII_PORT`) |
| PostgreSQL 18.6 | `127.0.0.1:5432` (`LEDGER_POSTGRES_PORT`), database `ledger`, login `ledger_app` |

Port 8000 is never used on the host. `/livez` and `/readyz` answer on every app. To call the api with real
tokens, start the local Zitadel (compose profile `zitadel`): [deploy/local/zitadel/README.md](deploy/local/zitadel/README.md);
a stack started under its own project (`-p <name>`) gives its scripts the same `COMPOSE_PROJECT_NAME`.
An app run on the host takes `LEDGER_*` variables (see `deploy/local/compose.yaml`'s header) and sets
`LEDGER_HTTP_PORT=8101` for the worker and 8103 for the receiver (8100, the api's, is the default).

The signer (ADR 0010) holds the certificates and signs, in a container of its own: the login `ledger_signer`,
the only one that enters the schema `signer`, and a gRPC service on `signer:50051`, never published on the host
(it has no gRPC health service: it is probed over HTTP). It shares the internal network `signer` with its callers
and PostgreSQL alone, so nothing else in the stack reaches 50051; its own network `signer-edge` carries its probe
port and, locally, a route out (a deployment's NetworkPolicy admits gRPC from the api, the worker and the
receiver only, and lets it reach PostgreSQL and the KMS only). The api, the worker and the receiver call it with
a token each; `deploy/local/signer/tokens.sh` writes three random ones (api, worker, receiver) into
`deploy/local/signer/.local/`, the signer reads all three and each caller only its own (`--new` replaces them:
recreate the api, the worker, the receiver and the signer). Without the signer's file compose refuses to start
the stack; its callers start without theirs. No caller's readiness depends on the signer: without it the
certificate routes answer 503 `signer_unavailable`. Its KMS is a key file in the volume
`signer-kms`, refused outside the environments `local` and `test`, so the signer runs nowhere but here and in the
tests yet. [docs/runbooks/signer/](docs/runbooks/signer/) has the rest.

The api holds every credential to a rate of its own, per replica, behind the ingress's limit (spec §10):
`LEDGER_RATE_LIMIT_PER_SECOND` (default 50) and `LEDGER_RATE_LIMIT_BURST` (default 100, the requests it may make
at once). Over it a request is answered 429 with `Retry-After`. Each replica remembers 10 000 credentials; when
all are active the oldest is set aside with what it used (1 000 more at most), so a new caller never waits for
room and no allowance is reset short of 11 000 credentials active at once.

The receiver proves no token of ours (its callers are the tax authority and other emitters, proven by each
channel's own seeds, tokens and signatures). It holds each client address to `LEDGER_RECEIVER_RATE_PER_SECOND`
(default 20) and `LEDGER_RECEIVER_RATE_BURST` (default 40), per replica; behind an ingress,
`LEDGER_RECEIVER_FORWARDED_HOPS` names the proxies that append to `X-Forwarded-For` (default 0: never read).
Paths under a channel's key are case-insensitive, as DGII calls them.

do-ecf-v1 talks to the stack's fake DGII (`deploy/local/do-ecf.env`; `ledger-fake-dgii` from
`countries/do/testing`, never in the image), so the local stack issues, delivers and receives e-CF end to end
without DGII. Against DGII's own TesteCF and CerteCF: [docs/runbooks/do/testecf.md](docs/runbooks/do/testecf.md)
and [certecf.md](docs/runbooks/do/certecf.md).
